# zbox CLI

Wrapper around the zbox orchestrator. The standalone `../zbox-gui` is retired: the per-workspace console is served by the orchestrator, the Zerops GUI (`~/code/zerops/frontend`) does login, register and the workspace key hand-over, and the CLI lists, creates and deletes workspaces itself. The orchestrator itself lives in `../nest` (`pkg/zerops/orchestrator/zbox`, branch `z0-zbox`), design in `../nest/sandbox-workspace-architecture.md`, decisions and gotchas in `../nest/pkg/zerops/orchestrator/zbox/CLAUDE.md`, older notes in `~/.claude/plans/zbox.md`.

Terminology: one Zerops service is one **workspace**. Say "workspace" in code and output, never "pool". The persisted key `serviceId` in `config.json` keeps its spelling.

## The contract

The API is `../nest/pkg/zerops/orchestrator/zbox/generated/openapi/restPublic/openapi.yml` (73 routes, v0, bearer API key on everything but ping). The CLI is built against the contract, not against the deployed backend: the nest session implementing the endpoints announces finished route groups, and every route exists as a stub until then. Nothing exists in the CLI that is not in the spec.

Contract changes go through the nest side. If a shape blocks the CLI or is wrong for it, name the route and the reason to the nest session, do not work around it locally.

## Generated client

`internal/api/gen.go` is generated by oapi-codegen (a `tool` directive in `go.mod`, config `internal/api/oapi.yaml`) straight from the nest file. Regenerate after every spec change:

```sh
go generate ./internal/api
```

`internal/api/client.go` is the hand-written wrapper: `Workspace` (the generated type is already called `Client`) adds the bearer, mints an `Idempotency-Key` per capacity-consuming call (`Key()`), decodes every 200 into the shared `Base*` type and every error into `ApiError`, and adds the waits (`WaitOperation`, `WaitSandbox`) and the two WebSocket routes (`Shell`, `StreamEvents`). The contract types timestamps as plain strings (`format: dateTime`), `api.Time` parses them. Both error shapes are decoded, the flat `{code, message}` of the spec and the `{"error": {...}}` envelope of the shared HTTP server.

## Command conventions

- Every command takes `--json` and then prints the API objects untouched. The text form goes through `emit(v, func())` in `cmd/root.go`.
- Mutations that answer with an operation wait for it by default and exit non-zero when it fails, `--no-wait` prints the operation instead. An `operationInFlight` answer (another capacity operation still runs, its id in the error metadata) makes the command wait on that operation and retry once, unless `--no-wait`. `invalidSandboxStatus` is a settled state that does not allow the verb and is reported as is. `zbox new`, `fork` and `restore` answer with a Spawn (operation plus rows), `runSpawn` waits on the operation and re-reads the rows.
- Bases and templates are addressed by digest, digest prefix, image ref or name (`findBase`, `findTemplate`). `zbox new` with no `--base` uses the only ready base and refuses to guess between several.
- Ports are declared in the sandbox policy: `port[/protocol][/access]` (`3000`, `3000/public`, `5432/tcp/project`, plus `websocket`, `wake` and `no-wake` tokens; public ports do not wake a parked sandbox unless `wake` says so). `zbox port open|close` read the policy and write it back under the generation they read, so a concurrent edit is rejected rather than merged. The URL of a port is `{port}-{id}-{ingress-host}`, the API returns it in `hosts`, which is derived from the HTTP ports only, so port listings read `policy.ingress.ports` and attach the URL where one exists. Text output prints URLs ready to open (`openUrl`): a MEMBERS port carries `?apiKey=<workspace key>`, `zbox cred issue` prints the port URL with `?ticket=` or `?token=` and the fresh secret, the router exchanges the parameter once for a `zbox_session` cookie and redirects to the clean URL. PUBLIC stays bare, PROJECT has no URL. `--json` prints the API objects untouched, so the bare `hosts` are there.
- `zbox new` on a plain image such as `alpine` needs a long-running command after `--` (docker runs the image contract as the container command), otherwise the sandbox fails at once.
- `exec` and `process` take argv after `--`, no shell. `zbox exec` exits with the remote exit code.
- `zbox shell` speaks the PTY WebSocket: the first server frame is text `{"session":{id,ticket}}`, binary frames are terminal bytes, a text `{"resize":...}` follows SIGWINCH. Shell exit closes 1000, a refused open or resume closes 4000 with `<code>: <message>` as the reason (`closeReason` turns it into the usual `ApiError`), only a 1006 is a real drop: it is resumed with `?sessionId=&sessionTicket=` for a minute, and a resume answered `sessionNotFound` means the shell had exited meanwhile, so the command ends cleanly. Stdin is read once and handed to the current connection so a reconnect loses nothing.
- `zbox webhook create` with no `--event` (or `--event all`) sends an empty list, which the contract reads as every event; listings print it as `all`. The signing secret is printed once at creation. `zbox ssh-key` takes a public key file, not the key text. Integration attachments are rows only in v1, the credential proxy behind the `http://<label>.int.<workspace-domain>/` address is not built yet.
- Policies (workspace, template, sandbox) are edited as JSON files: print, edit, `-f file` back. `zbox policy <id>` prints the shape `-f` takes, generation included.

## Iteration loop

Build straight into the user's PATH after every change, they test by hand from there:

```sh
go build -o ~/.local/bin/zbox .
```

`zbox login` and `zbox register` open the Zerops GUI by default and receive a personal access token on a loopback hand-over (`internal/browser`), the machinery Zerops Code uses: the CLI opens `<gui>/authorize-app?app=zbox&state=<nonce>&port=<port>` (`&intent=register` for register), the GUI redirects the browser to `http://localhost:<port>/zerops/authorized` with the credential in the **fragment** (`#token=&state=`, or `#error=<code>&state=`), and the callback page the CLI serves posts the fragment to `/zerops/authorized/deliver` and scrubs it from history. The receiver listens on 127.0.0.1 and ::1, checks the nonce, and maps the GUI's codes (`access_denied`, `mint_failed`, `workspace_not_found`, `reveal_failed`, `workspace_not_ready`) to `HandoverError`; `authorize` waits for the `zeropsSubdomain` env before opening the browser so the last one is not met. `browser_test.go` plays the GUI and the browser against it. `--token` stores a given token; `--email` (with `--password`, asked for without echo) logs in from the terminal through `POST /auth/login` and mints the token itself (`POST /user-token`), which cannot answer two-factor authentication and cannot be exercised with a token (`notAllowedForApplicationToken`). The GUI origin is `guiUrl` in the config, `--gui-url` for one run, and by default `http://localhost:1111`, the Zerops GUI dev server on this machine (`~/code/zerops/frontend` against the futon API): a development default until the hand-over is deployed, the deployed origin is not settled.

The same hand-over delivers the workspace API key, which is a generated secret the public API does not reveal to a token: `zbox workspace authorize <service-id>` opens `intent=workspace&serviceStackId=`, the GUI reveals the env (the user gets a password prompt for sudo mode), answers `#apiHost=&apiKey=&serviceStackId=&state=`, and the CLI only stores the key: the workspace lands in the list under the service hostname (`--name` overrides) and becomes the current one only when none is (`config.Remember` versus `Assign`). `zbox setup` lands in the same function when the env read gives the `<@` placeholder, with the wait screen paused (`Pause`/`Resume`) while the browser is open, and switches to it. `zbox workspace ls` lists the workspaces of the logged-in account, which in v0 are its docker services (a service stack search on `clientId` and `serviceStackTypeId`; the search index does not carry `recipeSource`, so the marker is only sent on import), with the name and an asterisk for the ones this machine holds a key for, and the `use`-assigned ones that are not in the account after them; not logged in, it lists the known ones. The standalone zbox GUI is retired: the per-workspace console is served by the orchestrator at `/` of the API host (`zbox open` opens `/console/login?apiKey=<key>`, which sets the `zbox_console` cookie and redirects to `/`, a wrong key lands on the console's login form; `zbox workspace key` prints the key for pasting), and the Zerops GUI does only login, register and the key hand-over for zbox (`~/code/zerops/frontend`, page `/authorize-app`).

Config keys: `workspaceUrl` (the API host, first line of the service's `zeropsSubdomain`) and `apiKey` (the `apiKey` service env) are the workspace in use, and `workspaces` is the list of known ones (name, Zerops ids, URL, key), the current one included. Every reader keeps using the flat fields; `zbox switch <name|host|prefix|service id>` copies another entry into them without contacting anything, `zbox workspace ls` lists the account's workspaces with the known ones marked, `zbox setup --name`, `zbox workspace use --name` and `zbox workspace authorize --name` add entries (a name in use by another workspace is refused, the default name of a `use` is the first host label), teardown and forget drop the current one and name the others. A config from before the list gets its flat workspace as the one entry at load. `ZBOX_WORKSPACE_URL` and `ZBOX_API_KEY` override the workspace for one run, `zbox workspace use <url> --api-key` assigns a workspace the CLI did not create (no Zerops ids, so no teardown).

Hidden flags: `--public-api-url` (default futon), `--gui-url`, `--image-url` (default sandbox image tarball baked into the import YAML).

The orchestrator binary is no longer downloaded: since 2026-09-15 it is a zstart user-target package (`zerops-zbox-orchestrator`) mounted into every docker VM at `/opt/zerops/bin/zerops-zbox-orchestrator`, so an orchestrator change reaches a workspace with the platform and a service restart. The bucket still holds an old `zbox` object nothing reads any more.

`zbox-base.tar.gz` is a `docker save` of the default sandbox image, which the import YAML pipes into `docker load` as an init command (the orchestrator has no image loading of its own). Rebuild it whenever the Dockerfile in the orchestrator changes. `--provenance=false --sbom=false` keeps it a plain single-platform image, docker 26.1 in the workspace cannot load a buildx manifest list:

```sh
cd ../nest/pkg/zerops/orchestrator/zbox/service/substrate/docker/assets
docker build --platform linux/amd64 --provenance=false --sbom=false -t zbox-base:latest .
docker save zbox-base:latest | gzip -1 > /tmp/zbox-base.tar.gz
mc cp /tmp/zbox-base.tar.gz <alias>/57fhv-s3/zbox-base.tar.gz
```

## Setup and the default base

The import YAML publishes two http ports with subdomain access (8080 API, 8081 ingress, the two lines of `zeropsSubdomain` the orchestrator reads itself, so 8080 must stay declared before 8081), and the router listener defaults to 8081 in the orchestrator config (`ZBOX_ROUTER_ADDRESS`) so no start-command flag is needed. Until the router lands, 8081 answers nothing and setup must not wait on it: readiness is the API on 8080. The YAML runs the mounted `/opt/zerops/bin/zerops-zbox-orchestrator`, generates the `apiKey` secret env, which the orchestrator reads from its own environment (the start line stays a plain command: Zerops runs it through `exec`, so a leading `VAR=value` fails with exit 127), creates `/var/lib/zbox` owned by `zerops` first, because the service runs as that user with only `/var/www` writable and the orchestrator keeps its sqlite file there, runs `migrate` as an init command before the image load (the orchestrator does not migrate at start, `migrate` creates the database when missing, applies the pending migrations and exits non-zero on failure, and `run` on an unmigrated database fails with "no such table"), and loads the tarball only when `zbox-base:latest` is not in docker yet, so a restart does not download it again. `--image-url` (hidden) is the tarball URL.

`zbox setup` imports the service with `recipeSource: zeropsio/zbox` in the request body (the marker the Zerops GUI lists workspaces by, `zeropsSetup` is not returned by the public API), waits for the Zerops processes, reads `zeropsSubdomain` and `apiKey` from the service envs, waits for `GET /workspace` to answer with the key, then registers `zbox-base:latest` (`--image`) through `POST /base` and waits for it to be READY. On docker the pull is synchronous and a locally loaded image is accepted when the pull fails, so the answer is already READY or `substrateFailed`. A workspace with no ready base cannot serve `zbox new`. The deployed zbox-test on futon runs the mounted orchestrator (API `https://zbox-c-8080.app-futon.zerops.dev`, ingress `-8081`), and a fresh `zbox setup` gets the generated `apiKey` through the GUI hand-over once the `/authorize-app` page ships for zbox; until then it stops at the placeholder and `zbox workspace use <api-url> --api-key <key>` is the way in. Per-port ingress URLs work on futon since the edge change of 2026-09-14 (the project L7 config gets a regex alias per subdomain host); every URL in `hosts` is reachable, all access modes, wake-on-request and GONE verified. A port nobody listens on behind the edge answers the platform's HTML 502 page after about five seconds, not a router JSON error, and parking kills every session in the sandbox, so a server started with `zbox process` is gone after a wake.

The import YAML is duplicated wherever a GUI creates workspaces: the retired `../zbox-gui` (`src/lib/workspace.svelte.ts`, `importYaml`) diffed its copy against `internal/zerops/import.go` after substituting the URLs and hostname, and the Zerops GUI section under `/zbox/...` (`~/code/zerops/frontend`) inherits that rule. Tell the session working there when the template changes; the two copies must stay byte-identical apart from hostname and image URL.

## The setup wait

`zbox setup` takes minutes and has almost nothing to print, so `internal/waiting` draws it: a wavy `zbox` wordmark, a progress estimate and a rotating note. Rules that package lives by:

- The frame is redrawn in place by counting lines, so every frame must have the same height and no line may exceed the terminal width. `screen_test.go` guards both. While the frame is up, nothing may reach stdout except through `Step` and `Detail`, a stray `fmt.Println` lands in the middle of it.
- Stdout that is not a TTY (a pipe, CI) falls back to plain lines, and `NO_COLOR` drops the colour.
- The percentage is a curve against `--estimate` (3m) that reaches 95% there and creeps afterwards, never 100%. The stage floors in `cmd/setup.go` pull it forward when a stage lands early.
- The Zerops processes behind the import are deliberately not shown, the step name is the whole status. A failed process still fails the setup with its own message.
- The notes were duplicated in the retired `../zbox-gui` (`src/lib/notes.ts`); a GUI that draws the same wait should reuse them. They are only ever accurate, useful things about a workspace: no jokes, no filler, and never soften a cost or a restart. Two wrapped lines each is the room they get.

## Gotcha

The public API answers a deleted project or service with **HTTP 400 and code `projectNotFound` / `serviceStackNotFound`**, not 404, even though the ACL middleware that raises them was meant to answer 404. `zerops.IsNotFound` matches the code and accepts 404 too, so a fix on the API side keeps working. Use it instead of checking the status.
