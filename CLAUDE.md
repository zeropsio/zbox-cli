# zbox CLI

Wrapper around the zbox orchestrator. The standalone `../zbox-gui` is retired: the per-workspace console is served by the orchestrator, the Zerops GUI (`~/code/zerops/frontend`) does login, register and the workspace key hand-over, and the CLI lists, creates and deletes workspaces itself. The orchestrator itself lives in `../nest` (`pkg/zerops/orchestrator/zbox`, branch `z0-zbox`), design in `../nest/sandbox-workspace-architecture.md`, decisions and gotchas in `../nest/pkg/zerops/orchestrator/zbox/CLAUDE.md`, older notes in `~/.claude/plans/zbox.md`.

Terminology: one Zerops service is one **workspace**. Say "workspace" in code and output, never "pool". The persisted key `serviceId` in `config.json` keeps its spelling.

## The contract

The API is `../nest/pkg/zerops/orchestrator/zbox/generated/openapi/restPublic/openapi.yml` (78 routes, v0, bearer API key on everything but ping). The CLI is built against the contract, not against the deployed backend: the nest session implementing the endpoints announces finished route groups, and every route exists as a stub until then. Nothing exists in the CLI that is not in the spec.

Contract changes go through the nest side. If a shape blocks the CLI or is wrong for it, name the route and the reason to the nest session, do not work around it locally.

## Generated client

`internal/api/gen.go` is generated by oapi-codegen (a `tool` directive in `go.mod`, config `internal/api/oapi.yaml`) straight from the nest file. Regenerate after every spec change:

```sh
go generate ./internal/api
```

`internal/api/client.go` is the hand-written wrapper: `Workspace` (the generated type is already called `Client`) adds the bearer, mints an `Idempotency-Key` per capacity-consuming call (`Key()`), decodes every 200 into the shared `Base*` type and every error into `ApiError`, and adds the waits (`WaitOperation`, `WaitSandbox`) and the two WebSocket routes (`Shell`, `StreamEvents`). The contract types timestamps as plain strings (`format: dateTime`), `api.Time` parses them. Both error shapes are decoded, the flat `{code, message}` of the spec and the `{"error": {...}}` envelope of the shared HTTP server.

## Command conventions

- Every command takes `--json` and then prints the API objects untouched. The text form goes through `emit(v, func())` in `cmd/root.go`.
- Mutations that answer with an operation wait for it by default and exit non-zero when it fails, `--no-wait` prints the operation instead. An `operationInFlight` answer (another capacity operation still runs, its id in the error metadata) makes the command wait on that operation and retry once, unless `--no-wait`. `invalidSandboxStatus` is a settled state that does not allow the verb and is reported as is. `zbox new`, `fork` and `restore` answer with a Spawn (operation plus rows), `runSpawn` waits on the operation and re-reads the rows.
- Bases and templates are addressed by digest, digest prefix, image ref or name (`findBase`, `findTemplate`). `zbox new` with no `--base` uses the only ready base and refuses to guess between several. `zbox template create --warm` boots the base once and snapshots its memory: the row is BUILDING until READY (`hasMemory` true, about 18 s on futon) or FAILED with `failedReason`, and the command waits unless `--no-wait`. `--memory` and `--cpus` set the size the image is taken at, which is also the default of every sandbox spawned with `--template`; a spawn that names another size cold boots from the base instead of resuming (about 8 s against 2 s). A warm template may carry a warm-up (`zbox template create --warm --warmup 'claude --version'`, contract since 2026-09-23): a shell command run in the build guest through `/bin/sh -c` under the image's launch env and working dir before the memory is captured, so what it loads is resident in every spawn; the CLI refuses it without `--warm`, a non-zero exit or 10 minutes fails the build (`failedReason` carries the exit code and the output's tail, printed by the wait), and `template ls` (last column) and `get` (`Warm-up`) show it. Deleting a building template answers `inUse`. The receipt of a finished boot operation (CREATE, WAKE, FORK, RESTORE) is the free `result` object, `{address, resumedMemory, secretsDelivered}` (PARK gives `{memoryKept}`); `bootNote` reads `resumedMemory` and `zbox new`/`fork`/`restore` print `Boot: resumed from memory` or `cold boot` under each row (`childOf` finds the row's child of the bulk operation), `wake` appends it to its line, `zbox operation get` prints the whole result. Every finished operation also shows how long it took at millisecond resolution (`took`, `tookNote` in `cmd/root.go`: `395 ms`, `3.2 s`, `1m 12.3s`), as the TOOK column of `zbox operation ls`, the Took field of `operation get` and `in …` on the park, wake, rm and Boot lines; the user's rule (2026-09-22) is that no duration is ever printed in whole seconds, the API timestamps carry microseconds. The AGE column of the listings is an age, not a duration, and stays coarse.
- Ports are declared in the sandbox policy: `port[/protocol][/access]` (`3000`, `3000/public`, `5432/tcp/project`, plus `websocket`, `wake` and `no-wake` tokens; public ports do not wake a parked sandbox unless `wake` says so). `zbox port open|close` read the policy and write it back under the generation they read, so a concurrent edit is rejected rather than merged. The URL of a port is `{port}-{id}-{ingress-host}`, the API returns it in `hosts`, which is derived from the HTTP ports only, so port listings read `policy.ingress.ports` and attach the URL where one exists. Text output prints URLs ready to open (`openUrl`): `zbox cred issue` prints the port URL with `?ticket=` or `?token=` and the fresh secret, the router exchanges the parameter once for a `zbox_session` cookie and redirects to the clean URL. A MEMBERS port takes no workspace API key at all since 2026-10-01 (neither `?apiKey=` nor a bearer; the API and the WebSocket routes dropped the `apiKey` query parameter the same day, the key is a bearer there), it opens only with a one-time ticket like a TICKET port, and `POST /sandbox/{id}/ingress-credential` with kind TICKET is allowed for it (TOKEN still needs a TOKEN port). Listings print the bare URL; `zbox open <sandbox> [port]` (`openPort` in `cmd/workspace.go`, the port may be left out when the sandbox has one HTTP port) mints a ticket, or a token for a TOKEN port, named `zbox open` with a 60 s TTL at the moment of opening and opens the URL with it; a PUBLIC port opens bare, PROJECT has no URL. Scripts use a TOKEN port, never members. `--json` prints the API objects untouched, so the bare `hosts` are there.
- `zbox new` on a plain image such as `alpine` needs a long-running command after `--` (docker runs the image contract as the container command), otherwise the sandbox fails at once.
- Every sandbox argument takes the id or the name (`zbox shell app`, `zbox park bots`): `resolveSandbox` in `cmd/resolve.go` tries an argument shaped like an id (`^[a-z0-9]{8}$`) as one first and keeps it when it exists, otherwise looks the name up among the sandboxes that are not TERMINATED or ARCHIVED (a name is unique among live ones, the orchestrator refuses a duplicate at create, dead rows may reuse it); no match keeps the API's `sandboxNotFound`, several would name the ids. It runs as the `PreRunE` of the commands (`sandboxArgs`, `sandboxArgsAll` for `rm`) and rewrites the arguments in place, so the command bodies keep taking ids. Session, snapshot, lineage, export, webhook, credential and quarantine ids are not sandboxes and stay ids.
- `GET /sandbox-list` takes `status` as a repeatable string list since 2026-10-01 (`status=RUNNING&status=FAILED`, no longer a single enum; without it the live sandboxes, TERMINATED and ARCHIVED excluded; an unknown value is a 400 `invalidUserInput` with the valid set under the `status` metadata key). `zbox ls --status` is repeatable and also splits commas (`statusList`), upper-cases, and sends nothing when empty.
- `exec` and `process` take argv after `--`, no shell. `zbox exec` exits with the remote exit code.
- `zbox shell` speaks the PTY WebSocket: the first server frame is text `{"session":{id,ticket}}`, binary frames are terminal bytes, a text `{"resize":...}` follows SIGWINCH. Shell exit closes 1000, a refused open or resume closes 4000 with `<code>: <message>` as the reason (`closeReason` turns it into the usual `ApiError`), only a 1006 is a real drop: it is resumed with `?sessionId=&sessionTicket=` for a minute, and a resume answered `sessionNotFound` means the shell had exited meanwhile, so the command ends cleanly. Stdin is read once and handed to the current connection so a reconnect loses nothing.
- `zbox webhook create` with no `--event` (or `--event all`) sends an empty list, which the contract reads as every event; listings print it as `all`. The signing secret is printed once at creation. `zbox ssh-key` takes a public key file, not the key text. The credential proxy behind the `http://<label>.int.<ingress-host>/` address exists on the Firecracker substrate (the label lands in the guest's `/etc/hosts` at boot and on a live attach or detach; the proxy strips the Authorization and X-Api-Key the sandbox sent and injects the integration's credential as bearer, basic or a named header; peer attachments answer 501). Connectors (`zbox connector`) are the fixed catalogue on top of it: `claude`, `github`, `codex`, each a Workspace env (`CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY`, `GH_TOKEN`, `OPENAI_API_KEY`) plus the integrations it manages (`claude`, `github` and `github-api`, `openai`). `zbox connector set <name>` reads the value without echo or whole from a pipe, never from argv, and `PUT /connector/{name}/credential` stores it as a secret service env and applies it live; `unset` blanks the env and keeps the integrations; `login <name>` posts `/connector/{name}/login` and attaches the terminal (`attachShell`, the shell's resume path with the returned `sessionId` and `sessionTicket`, the session is detached with the 60 s grace running, so attach at once) to the helper sandbox where the provider's login command runs; the orchestrator harvests the credential from the terminal output, stores it and terminates the helper, which closes the shell with 1000, and the command then reads the connector back and fails unless it is CONNECTED. A connected connector makes `zbox new --integration claude --integration github --integration github-api` hand the sandbox the proxied endpoints with a placeholder token (`ANTHROPIC_BASE_URL`, a git `url.insteadOf` rewrite through `GIT_CONFIG_*`, `GITHUB_API_URL`), which is set only at create, fork, restore and a redeliver wake; `--secret <env>` delivers the real credential instead and wins over the placeholder. A ChatGPT login is stored as `CODEX_AUTH_JSON` and only delivered, as `/root/.codex/auth.json`.
- `GET /operation-list` is paged since 2026-09-21: newest first, 100 rows by default, 1000 at most, `beforeId` continues with older ones. `zbox operation ls` prints that default page, `--limit` asks for a number and `--all` pages back through everything (`listOperations`); `childOf` relies on a fresh spawn's operations being within the newest page of its sandbox. `zbox events` with no cursor asks for `newestFirst` and prints the answer turned around, so the latest event is the bottom line (`--before <id>` pages back, `--json` keeps the API's order); `--after` is the old oldest-first long poll and `--follow` the stream, both unchanged.
- `zbox mcp` (`cmd/mcp.go`, official `modelcontextprotocol/go-sdk`) serves the workspace as a stdio MCP server for Claude Code (`claude mcp add zbox -- zbox mcp`): `run_code {code, language, sandbox_id?, keep?, timeout_seconds?}` spawns from `--template` (the first READY one by default, `--base` for a cold boot), runs `python3 -c` / `node -e` / `bash -c` in `/workspace` and terminates the sandbox unless `keep`, answering stdout, stderr, the exit code and `create_ms` / `run_ms`; `kill_sandbox` terminates a kept one. The exec timeout is capped at 50 s because the edge answers 504 for any API request over 60 s. A sandbox passed by id is never destroyed by `run_code`. The text content is the readable transcript form, the structured content the same fields.
- `GET /workspace` carries `capacity` (`{cpus, memoryBytes, diskBytes}` of the VM as detected on the host: cores, MemTotal, the size of the data volume) and `usage` (`{runningSandboxes, parkedSandboxes, cpus, memoryBytes, diskBytes}`: cpus and memory are the sizes reserved by the RUNNING sandboxes, disk is the used space of the data volume across bases, templates, sandboxes and snapshots) since 2026-09-22. `zbox status` prints them as `Capacity:` and `In use:` lines under the orchestrator line (skipped when an older orchestrator answers zeros), `zbox workspace get` as fields (`capacityString`, `usageString`).
- Policies (workspace, template, sandbox) are edited as JSON files: print, edit, `-f file` back. `zbox policy <id>` prints the shape `-f` takes, generation included.

## Iteration loop

Build straight into the user's PATH after every change, they test by hand from there:

```sh
go build -o ~/.local/bin/zbox ./cmd/zbox
```

`zbox login` and `zbox register` open the Zerops GUI by default and receive a personal access token on a loopback hand-over (`internal/browser`), the machinery Zerops Code uses: the CLI opens `<gui>/authorize-app?app=zbox&state=<nonce>&port=<port>` (`&intent=register` for register), the GUI redirects the browser to `http://localhost:<port>/zerops/authorized` with the credential in the **fragment** (`#token=&state=`, or `#error=<code>&state=`), and the callback page the CLI serves posts the fragment to `/zerops/authorized/deliver` and scrubs it from history. The receiver listens on 127.0.0.1 and ::1, checks the nonce, and maps the GUI's codes (`access_denied`, `mint_failed`, `workspace_not_found`, `reveal_failed`, `workspace_not_ready`) to `HandoverError`; `authorize` waits for the `zeropsSubdomain` env before opening the browser so the last one is not met. `browser_test.go` plays the GUI and the browser against it. `--token` stores a given token; `--email` (with `--password`, asked for without echo) logs in from the terminal through `POST /auth/login` and mints the token itself (`POST /user-token`), which cannot answer two-factor authentication and cannot be exercised with a token (`notAllowedForApplicationToken`). The GUI origin is `guiUrl` in the config, `--gui-url` for one run, and by default `https://futon.devel.zerops.dev` (`config.DefaultGuiUrl`, futon since 2026-10-01; the deployed alpha GUI `http://alpha.devel.zerops.dev` was the default from 2026-09-22 and serves the hand-over as well, the plain http origin redirects to https); `--gui-url http://localhost:1111` points a run at the GUI dev server on this machine (`~/code/zerops/frontend`).

The same hand-over delivers the workspace API key, which is a generated secret the public API does not reveal to a token: `zbox workspace authorize <service-id>` opens `intent=workspace&serviceStackId=`, the GUI reveals the service env `ZBOX_WORKSPACE_API_KEY` (the user gets a password prompt for sudo mode; since 2026-09-17 there is no fallback to the old `apiKey` env, so a workspace from before the controller answers `reveal_failed` with reason `no_api_key_env` until the env is added by hand), answers `#apiHost=&apiKey=&serviceStackId=&state=`, and the CLI only stores the key: the workspace lands in the list under the service hostname (`--name` overrides) and becomes the current one only when none is (`config.Remember` versus `Assign`). `zbox setup` lands in the same function when the key env is not readable to the token (absent after 30 s, empty, a generator placeholder, or the literal `REDACTED` that a read-only project role gets for a sensitive env; a personal access token is always in sudo mode, so it normally reads the generated key in clear from `GET /service-stack/{id}/env`), with the wait screen paused (`Pause`/`Resume`) while the browser is open, and switches to it. `zbox workspace ls` lists the workspaces of the logged-in account, which are its Sandbox Workspace services (one service stack search on `clientId` and `serviceStackTypeId` `sandbox_workspace`, `zbox@1` is only the import alias of that type; the docker services the v0 workspaces were imported as are not listed since 2026-09-21, when the docker substrate was removed from the orchestrator, and one this machine still holds a key for shows up among the ones not in the account; the search index does not carry `recipeSource`, so the marker is only sent on import), with the name and an asterisk for the ones this machine holds a key for, and the `use`-assigned ones that are not in the account after them; not logged in, it lists the known ones. The standalone zbox GUI is retired: the per-workspace console is served by the orchestrator at `/` of the API host (`zbox console` mints a single-use 60 s ticket with `POST /console/login-ticket`, a hand-registered console route outside the OpenAPI spec, `ConsoleLoginTicket` in `client.go`, and opens `/console/login?ticket=`, which sets the `__Host-zbox_console` cookie and redirects to `/`; the key never appears in a URL since 2026-09-24, a spent or expired ticket lands on the console's login form, and a 404 on the mint means an orchestrator from before that day; `zbox workspace key` prints the key for pasting), and the Zerops GUI does only login, register and the key hand-over for zbox (`~/code/zerops/frontend`, page `/authorize-app`).

Config keys: `workspaceUrl` (the API host, first line of the service's `zeropsSubdomain`) and `apiKey` (the `ZBOX_WORKSPACE_API_KEY` service env) are the workspace in use, and `workspaces` is the list of known ones (name, Zerops ids, URL, key), the current one included. Every reader keeps using the flat fields; `zbox switch <name|host|prefix|service id|project>` copies another entry into them without contacting anything (`config.Lookup`, see the override below for what it matches), `zbox workspace ls` lists the account's workspaces with the known ones marked, `zbox setup --name`, `zbox workspace use --name` and `zbox workspace authorize --name` add entries (a name in use by another workspace is refused, the default name of a `use` is the first host label), teardown (which deletes only the workspace service, never the project, so it also works on an authorized workspace) and forget drop the current one and name the others. A config from before the list gets its flat workspace as the one entry at load. `ZBOX_WORKSPACE_URL` and `ZBOX_API_KEY` override the workspace for one run, `zbox workspace use <url> --api-key` assigns a workspace the CLI did not create (no Zerops ids, so no teardown).

The global flag `--workspace <ref>` and the env `ZBOX_WORKSPACE` (since 2026-09-29, the flag wins) name a known workspace for one run and leave the current one as it is, which is how two sessions share one `config.json`: the nest session runs its benchmarks against `zboxbench` while the user keeps using their own. The ref goes through `config.Lookup`, against the stored `workspaces` only, nothing is contacted: a whole match on the name, the service id, the project name or id, the API URL or host, and only when nothing matches whole a prefix of the name or the host. A ref that fits several workspaces is refused with the candidates (name, project, service id, host), never settled by the order of the list, so a project that holds two workspaces does not name either; the service hostname is not stored and matches only as the default name of an authorized workspace. An unknown ref or an entry with no key fails with the hint to `authorize` or `use`. The mechanism is `config.Pin`: it answers a copy of the config whose flat fields show the named workspace and keeps the stored selection in the unexported `pinned`, which `Save` writes back, so every reader of the flat fields works unchanged and an override never becomes the current workspace; `EffectiveWorkspace` does not let `ZBOX_WORKSPACE_URL` and `ZBOX_API_KEY` override a pinned workspace, and `ZBOX_WORKSPACE` beside either of them in the environment is refused as contradictory. In `cmd`, `loadSelected` is the pinned config and what the commands that work on a workspace read (`workspace()`, `ensureWorkspace`, `status`, `teardown`, `workspace forget`), `loadConfig` stays the stored one for the commands that manage the selection (`switch`, `use`, `authorize`, `setup`, `workspace ls`, the login ones). So `teardown` and `forget` under an override act on the named workspace and the current one stays (`ForgetWorkspace` falls back to the stored selection, unless that was the very workspace). `zbox switch <ref>` and `zbox setup` refuse to run under an override (`refuseOverride`), `zbox switch` with no argument still lists. `zbox workspace use` under an override only stores the workspace (`Remember` instead of `Assign`) and the ref has to resolve to the workspace being stored, so a `ZBOX_WORKSPACE` left in the environment cannot pass for a request to keep the selection; `authorize` is unchanged, it only ever stored. The listings mark the named workspace with `>` beside the `*` of the current one and explain it in a line underneath (`mark`, `printMarks`), an unresolvable ref does not fail a listing, and `zbox status` names the override on its Workspace line.

Hidden flags: `--public-api-url` (default futon since 2026-10-01, alpha from 2026-09-22 before that, `config.DefaultApiUrl`; a stored `apiUrl` wins, and `zbox login --public-api-url <url>` is how a config moves environments, since `storeLogin` saves the URL with the token), `--gui-url`.

## Setup and the default base

Since 2026-10-06 the Sandbox Workspace type `zbox@1` (alias `zbox@latest`) is a managed (STANDARD) service type, no longer a runtime: no appVersion, no deploy, no zerops.yml, and the import refuses `minContainers`, `maxContainers`, `zeropsSetup`, `zeropsYaml` and `buildFromGit` for it. The import YAML (`internal/zerops/import.go`) is the type, `enableSubdomainAccess: true`, `verticalAutoscaling` with min equal to max and the env `ZBOX_WORKSPACE_BASES`. The controller publishes the two http ports itself (8080 API, 8081 ingress) and writes `zeropsSubdomain` as two lines, the API host first, which zsc copies into the orchestrator's config file; the router listener defaults to 8081 in the orchestrator config. Readiness is the API on 8080, setup never waits on 8081. The service is an Ubuntu VM in which the orchestrator runs Firecracker guests (its only substrate since 2026-09-21: the docker one and the `ZBOX_SUBSTRATE_KIND` env are gone, and the `substrate` field of `GET /workspace` only ever says FIRECRACKER), pinned to one container of 24 dedicated cpus, 128 GB of RAM and a 250 GB disk by default since 2026-09-22 (the alpha nodes are metal, 32 to 64 cores and 251 GB; `--cpu`, `--ram` and `--disk` go smaller; the type has no vertical scaling, which the API enforces by refusing a differing pair, and the driver floor is 2 cpu, 2 GB, 10 GB, which `RenderImport` refuses to go under). The disk is the XFS data volume at `/var/lib/zbox`, one shared pool for every base, sandbox disk, park image and snapshot (a sandbox root is a sparse 10 GiB image from the orchestrator config, not a per-sandbox share of it), the root disk is a fixed 5 GiB, and guests take their RAM from the VM's, 1 GiB each by default. Since 2026-10-07 zsc runs the mounted `/opt/zerops/bin/zerops-zbox-orchestrator` from the image like this, everything as root (no sudo re-exec any more): before every start it writes `/etc/zerops-zbox-orchestrator/config.yml` (root, 0600) from the service env, `zbox.workspace.{apiKey, masterKey, apiHost, ingressHost, bases}`, the hosts taken from the two `zeropsSubdomain` URLs (API first), the bases from the plain user env `ZBOX_WORKSPACE_BASES`, and the orchestrator reads only that file for its own configuration, no service env; then it runs the one command `zerops-zbox-orchestrator prepare` (mounts the XFS data volume, formatting a blank disk and growing it on a disk change, checks the image contract, loads kernel modules and sysctls, fetches the guest kernel, builds the nft table and applies the SQLite schema migrations); then it starts the systemd unit `zerops-zbox-orchestrator` (`ExecStart=/opt/zerops/bin/zerops-zbox-orchestrator run`, root, no zenv) and waits for `GET /api/rest/ping`. Nothing from the import runs commands. The orchestrator logs to the local syslog under the tag `zerops-zbox-orchestrator`, zsc's own lines are tagged `zerops@setup`, and both reach the project log (`zcli service log`, the GUI), the prepare lines included. The orchestrator carries no key of its own since 2026-09-17: the controller generates the sensitive system env `ZBOX_WORKSPACE_API_KEY` at service create (like the Qdrant `apiKey`), and since 2026-10-07 it reaches the orchestrator only through the config file. The bases come from `ZBOX_WORKSPACE_BASES`: image references or `docker save` tarball URLs separated by whitespace or commas, each pulled and flattened by `run` in the background once the API listens (since 2026-10-07 evening; `prepare` pulled them before the unit for a few hours that day, which made a slow registry gate the service start), so the service turns ACTIVE before the bases are in place and the setup wait covers the pull (a few minutes on a first setup; idempotent per digest; a failed pull is a line in the project log, the base has no row, `zbox base ls` shows nothing for it, the next start tries again). The platform has no default, `zbox setup` writes the image (`--image`, the tarball URL by default) as the value and the GUI will too. An edited `ZBOX_WORKSPACE_API_KEY` or `ZBOX_WORKSPACE_BASES` takes effect on the next explicit restart, stop and start, or reload of the service, never on its own; the reload (on the type since 2026-10-07) is the cheap way, it runs stop unit, config, prepare, start without rebooting the VM, so the sandboxes stay up, while a restart reboots the VM and parks every sandbox. So adding a base to an existing workspace is an edit of the env and a reload, which replaces the old `zcli push` of a rendered yaml. `RenderImport` holds the image to a plain reference charset, since the value is split on whitespace and commas. Templates are not built at start any more: `zbox setup` creates them through `POST /template` once the base is READY (point 3 of the nest brief of 2026-10-06), one after the other, each a step on the waiting screen ("Building the warm template dev"), with name, the base digest, memory, cpus, warm true and the warm-up, exactly what `zbox template create --warm` sends (`createSetupTemplate`, `waitTemplate` in `cmd/base.go`); `--template name[:memory[:cpus]]` keeps the defaults `dev:4g:2` and `big:16g:4`, the first `--template` replaces both and `--template none` builds none, `--warmup name=command` is repeatable with one per template name (`setupTemplates`, `setupTemplate` in `cmd/setup.go`). A failed build ends the setup with the template's `failedReason` after the ready line, the workspace is up and `zbox template create --warm` builds it again. The VM names on the node are `<hostname>-db-1-N` since the type change (the driver service key is `db`), `<hostname>-runtime-1-N` before. `prepare` mounts the data disk at `/var/lib/zbox`, and there is no image load, no docker. A workspace cannot be re-deployed any more, there is nothing to deploy; a service stop and start keeps the data. The runtime-era yaml with the init commands (`migrate`, `host prepare`, `base ensure`, `template ensure` lines) is in git history (v0.16), the docker@26.1 template before it (v0.5); the init-command era of 2026-10-06, in which zsc ran `host prepare`, `migrate` and `base ensure` lines and `run` through zerops-zenv, lasted one day.

`zbox setup` imports the service with `recipeSource: zeropsio/zbox` in the request body (the marker the Zerops GUI lists workspaces by, `zeropsSetup` is not returned by the public API), waits for the Zerops processes, reads `zeropsSubdomain` and `ZBOX_WORKSPACE_API_KEY` from the service envs (the key through the GUI hand-over when the env list does not give it to a token), waits for `GET /workspace` to answer with the key, then waits for the default base (the tarball URL, `--image` overrides): the row appears only when the pull is done, which `run` does in the background right after it listens, so `ensureBase` finds the row at `GET /base-list` by image ref within a minute or two (stored verbatim, and a digest registered again under another reference takes the newest one) and waits for READY (`setupBaseTimeout`, 15 min); it keeps looking for `setupBasePoll` (3 min), and only when no row shows up in that time, which is what a failed pull looks like, does it register the image through `POST /base` itself and get the pull's error back (a second pull of a registered ref is a no-op on the digest, so the fallback is safe, just slower). The answer is READY or `substrateFailed`. A workspace with no ready base cannot serve `zbox new`. A guest on this type reaches the internet and the project DNS, but not the workspace itself or other sandboxes. The docker-era workspaces on futon (such as `zbox` of project zbox-test) cannot run the orchestrator any more, it has no docker substrate; do not deploy to futon from here. A fresh `zbox setup` gets the generated `apiKey` through the GUI hand-over. Per-port ingress URLs work on futon since the edge change of 2026-09-14 (the project L7 config gets a regex alias per subdomain host); every URL in `hosts` is reachable, all access modes, wake-on-request and GONE verified. A port nobody listens on behind the edge answers the platform's HTML 502 page after about five seconds, not a router JSON error, and parking kills every session in the sandbox, so a server started with `zbox process` is gone after a wake.

The import YAML lives only in `internal/zerops/import.go` now: the retired `../zbox-gui` held a copy and the Zerops GUI does not create workspaces. The template is owned by the nest side (it mirrors what the controller of the type accepts), so a template brief from the nest session is applied as given, and a change made here is reported back there.

## The setup wait

`zbox setup` takes minutes and has almost nothing to print, so `internal/waiting` fills it with plain text: each stage is a line with trailing dots and, on a TTY, a dimmed note about workspaces follows every nine seconds. It used to be a redrawn frame with a wavy `zbox` wordmark and a progress bar, the user asked for text only (2026-09-16), so nothing is redrawn and there is no `--estimate` any more. Rules that package lives by:

- Stdout that is not a TTY (a pipe, CI) gets the stage lines only, and `NO_COLOR` drops the dimming.
- `Pause`/`Resume` hold the notes while the caller prints and reads on the terminal (the browser hand-over), so a note cannot land in the middle of a prompt.
- The Zerops processes behind the import are deliberately not shown, the step name is the whole status. A failed process still fails the setup with its own message.
- The notes were duplicated in the retired `../zbox-gui` (`src/lib/notes.ts`); a GUI that draws the same wait should reuse them. They are only ever accurate, useful things about a workspace: no jokes, no filler, and never soften a cost or a restart. Keep them to a sentence or two, they wrap like any other line.

## Gotcha

The public API answers a deleted project or service with **HTTP 400 and code `projectNotFound` / `serviceStackNotFound`**, not 404, even though the ACL middleware that raises them was meant to answer 404. `zerops.IsNotFound` matches the code and accepts 404 too, so a fix on the API side keeps working. Use it instead of checking the status.
