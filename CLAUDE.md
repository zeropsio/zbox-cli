# zbox CLI

Wrapper around the zbox orchestrator. The standalone `../zbox-gui` is retired: the per-workspace console is served by the orchestrator, the Zerops GUI (`~/code/zerops/frontend`) does login and register, and the CLI lists, creates and deletes workspaces itself. The orchestrator itself lives in `../nest` (`pkg/zerops/orchestrator/zbox`, branch `z0-zbox`), design in `../nest/sandbox-workspace-architecture.md`, decisions and gotchas in `../nest/pkg/zerops/orchestrator/zbox/CLAUDE.md`, older notes in `~/.claude/plans/zbox.md`.

Terminology: one Zerops service is one **workspace**. Say "workspace" in code and output, never "pool". The persisted key `serviceId` in `config.json` keeps its spelling.

## The contract

The API is `../nest/pkg/zerops/orchestrator/zbox/generated/openapi/restPublic/openapi.yml` (78 routes, v0, bearer API key on everything but ping). The CLI is built against the contract, not against the deployed backend: the nest session implementing the endpoints announces finished route groups, and every route exists as a stub until then. Nothing exists in the CLI that is not in the spec.

Contract changes go through the nest side. If a shape blocks the CLI or is wrong for it, name the route and the reason to the nest session, do not work around it locally.

## Generated client

`internal/api/gen.go` is generated by oapi-codegen (a `tool` directive in `go.mod`, config `internal/api/oapi.yaml`) straight from the nest file. Regenerate after every spec change:

```sh
go generate ./internal/api
```

`internal/api/client.go` is the hand-written wrapper: `Workspace` (the generated type is already called `Client`) adds the bearer (the zproxy access token, or the workspace key in direct mode, see "Reaching the workspace" below), renews an expired access once per request through `Renew` (the `renewing` transport, `X-Zerops-Ui-Session: expired` on a 401, the body rewound when `GetBody` allows, `ErrAccessRenewed` otherwise; `BuildBase` pings first since its body streams once), mints an `Idempotency-Key` per capacity-consuming call (`Key()`), decodes every 200 into the shared `Base*` type and every error into `ApiError`, and adds the waits (`WaitOperation`, `WaitSandbox`) and the two WebSocket routes (`Shell`, `StreamEvents`). The contract types timestamps as plain strings (`format: dateTime`), `api.Time` parses them. Both error shapes are decoded, the flat `{code, message}` of the spec and the `{"error": {...}}` envelope of the shared HTTP server.

## Command conventions

- Output, errors, exit codes, confirmations, waits and help follow `docs/cli-ux.md` (since 2026-10-09 evening, the user's brief: humans and agents both first-class). In short: an ASCII table (tablewriter v1, `newTable`/`fields` in `cmd/output.go`) on a terminal, TSV with a header when piped, the API objects untouched under `--json` (through `emit(v, func())`), ids only under `-q`; progress and hints on stderr through `note()`; errors as one JSON object on stderr under `--json`, exit codes 1 failed, 2 usage, 3 not found, 4 conflict, 5 timeout, 6 unauthorized, 7 unavailable, 125 own failure of `exec`, 130 interrupted (`cmd/errors.go`); destructive commands `confirm()` on a TTY and need `--yes` otherwise, and every multi-target delete goes through `deleteEach` (one confirmation, one line per target, `[{id, operation}]` under `--json`); waiting commands take `--no-wait` and `--timeout`; `park` and `wake` succeed on a sandbox already in the target state. Read that file before adding a command. Since 2026-10-14 the primary name of a command is the full word and the short form is a cobra alias (`list`/`ls`, `remove`/`rm`, `rename`/`mv` on sandboxes, bases and templates, `workspace`/`ws`, `new`/`create`, beside the older `op`, `cred`, `snap`, `int`), the variables keep their old names (`lsCmd`, `rmCmd`); help text and hints say the full word. Everything that manages a workspace is under `zbox workspace` (`status`, `switch`, `console`, `teardown` moved there that day), only `zbox setup` stays at the top; every top-level command is in a group of `cmd/groups.go`, cobra's "Additional Commands" list is not to appear.
- Mutations that answer with an operation wait for it by default and exit non-zero when it fails, `--no-wait` prints the operation instead. An `operationInFlight` answer (another capacity operation still runs, its id in the error metadata) makes the command wait on that operation and retry once, unless `--no-wait`. `invalidSandboxStatus` is a settled state that does not allow the verb and is reported as is. `zbox new`, `fork` and `restore` answer with a Spawn (operation plus rows), `runSpawn` waits on the operation and re-reads the rows.
- Bases and templates are addressed by digest, digest prefix, image ref or name (`findBase`, `findTemplate`; bases carry a name since 2026-10-09, tried first). `zbox base add <ref> --name x` and `zbox base build [dir|archive] --name x` take the name over from the base that held it, so a rebuild under the same name is what `zbox new --base x` boots next; `zbox base set <base> --name y` renames and refuses `nameConflict`, `--name ''` drops it. `zbox base build` packs the directory (the current one by default, modes and symlinks kept as they are, a `Dockerfile` at its root required) into a tar.gz in a temporary file; what stays out is what `docker build` leaves out (`cmd/context.go`, `packDir` and `ignorer`, since 2026-10-09 evening): the root `.dockerignore` when there is one, with Docker's exact semantics through `github.com/moby/patternmatcher` (a directory is pruned whole unless a `!` line could bring a child back), the tree's `.gitignore` files otherwise (every line compiled on its own with `github.com/sabhiram/go-gitignore`, the last matching line of the deepest file decides, an ignored directory is pruned, nested files are read as the walk enters their directory), `.git` always; the `Dockerfile` and the `.dockerignore` are always sent so BuildKit applies the file on the workspace too, and `.gitignore` is not read when a `.dockerignore` exists. One line names what was packed and what governed it (`packed 7 files, 4.4 KiB, 3 left out by .dockerignore`), `--verbose` lists every member with `+` and every file or pruned tree with `-`, `--dry-run` lists and uploads nothing; `zbox setup --build` prints the same per build (`-v` lists). Tests in `cmd/context_test.go`.  and posts it as the raw body of `POST /base-build?name=` (`BuildBase` in `internal/api/client.go` sets the Content-Length so the upload is not chunked), or sends a ready `.tar`, `.tar.gz` or `.zip` as it is; the answer is a `BUILD_BASE` operation the command waits on (`--no-wait` prints it), then it prints the base from the result's `digest` and the time it took. A failed build's error is the tail of the BuildKit log (`zbox operation ls` shows its first line, `operation get` all of it). `zbox base prune` removes the workspace's whole build cache (`DELETE /base-build-cache`), builds never prune on their own. Verified on futon 2026-10-09: an alpine Dockerfile with RUN, COPY, ENV, EXPOSE and CMD builds in 8 to 17 s, boots in under a second, the copied script keeps its mode. `zbox setup` since 2026-10-09 evening sends no base in the import (`ZBOX_WORKSPACE_BASES` is not set by the CLI any more, the orchestrator still honours it on a service that carries it) and runs a chain after the orchestrator answers: every `--build [name=]<dir|archive>` is packed before anything is created and built into a base (named after the directory or archive unless `name=` says otherwise, two builds of one name are refused), then every `--base [name=]<ref|tarball URL>` is registered with `POST /base` and waited for, then every `--template name=cpus:memory@base` (every part required since the user's rule of 2026-10-09 evening, no first-base default) is warmed on the base it names (a build or pull name, or a pull's ref; an unknown base or a repeated template name is refused before anything is created), with `--warmup name=command` as before. Without `--build` and `--base` the default tarball is pulled. `splitNamed` only treats a plain word before `=` as the name, so a URL or `image:tag` is never split. The summary names every base and template. Examples: `examples/hello-base` (Alpine, python server on 8080) and `examples/multistage-base` (two-stage Go build exercising ARG, LABEL, ADD of a tarball, COPY --chmod and --from, a symlink in the context, ENV, VOLUME, HEALTHCHECK, USER, ENTRYPOINT + CMD, .dockerignore); USER is not honoured by the sandbox, the workload runs as root. `zbox new` with no `--base` uses the only ready base and refuses to guess between several. `zbox template create --warm` boots the base once and snapshots its memory: the row is BUILDING until READY (`hasMemory` true, about 18 s on futon) or FAILED with `failedReason`, and the command waits unless `--no-wait`. `--memory` and `--cpus` set the size the image is taken at, which is also the default of every sandbox spawned with `--template`; a spawn that names another size cold boots from the base instead of resuming (about 8 s against 2 s). A warm template may carry a warm-up (`zbox template create --warm --warmup 'claude --version'`, contract since 2026-09-23): a shell command run in the build guest through `/bin/sh -c` under the image's launch env and working dir before the memory is captured, so what it loads is resident in every spawn; the CLI refuses it without `--warm`, a non-zero exit or 10 minutes fails the build (`failedReason` carries the exit code and the output's tail, printed by the wait), and `template ls` (last column) and `get` (`Warm-up`) show it. Deleting a building template answers `inUse`. The receipt of a finished boot operation (CREATE, WAKE, FORK, RESTORE) is the free `result` object, `{address, resumedMemory, secretsDelivered}` (PARK gives `{memoryKept}`); `bootNote` reads `resumedMemory` and `zbox new`/`fork`/`restore` print `Boot: resumed from memory` or `cold boot` under each row (`childOf` finds the row's child of the bulk operation), `wake` appends it to its line, `zbox operation get` prints the whole result. Every finished operation also shows how long it took at millisecond resolution (`took`, `tookNote` in `cmd/root.go`: `395 ms`, `3.2 s`, `1m 12.3s`), as the TOOK column of `zbox operation ls`, the Took field of `operation get` and `in …` on the park, wake, rm and Boot lines; the user's rule (2026-09-22) is that no duration is ever printed in whole seconds, the API timestamps carry microseconds. The AGE column of the listings is an age, not a duration, and stays coarse.
- Ports are declared in the sandbox policy: `port[/protocol][/access]` (`3000`, `3000/public`, `5432/tcp/project`, plus `websocket`, `wake` and `no-wake` tokens; public ports do not wake a parked sandbox unless `wake` says so). `zbox port open|close` read the policy and write it back under the generation they read, so a concurrent edit is rejected rather than merged. The URL of a port is `{port}-{id}-{ingress-host}`, the API returns it in `hosts`, which is derived from the HTTP ports only, so port listings read `policy.ingress.ports` and attach the URL where one exists. Text output prints URLs ready to open (`openUrl`): `zbox cred issue` prints the port URL with `?ticket=` or `?token=` and the fresh secret, the router exchanges the parameter once for a `zbox_session` cookie and redirects to the clean URL. A MEMBERS port takes no workspace API key at all since 2026-10-01 (neither `?apiKey=` nor a bearer; the API and the WebSocket routes dropped the `apiKey` query parameter the same day, the key is a bearer there), it opens only with a one-time ticket like a TICKET port, and `POST /sandbox/{id}/ingress-credential` with kind TICKET is allowed for it (TOKEN still needs a TOKEN port). Listings print the bare URL; `zbox open <sandbox> [port]` (`openPort` in `cmd/workspace.go`, the port may be left out when the sandbox has one HTTP port) mints a ticket, or a token for a TOKEN port, named `zbox open` with a 60 s TTL at the moment of opening and opens the URL with it; a PUBLIC port opens bare, PROJECT has no URL. Scripts use a TOKEN port, never members. `--json` prints the API objects untouched, so the bare `hosts` are there.
- `zbox new` on a plain image such as `alpine` needs a long-running command after `--`. On Firecracker a launch command that exits leaves the sandbox RUNNING with only `/init` (seen 2026-10-09 with `-- false`), it does not fail it as the docker substrate did.
- Every sandbox argument takes the id or the name (`zbox shell app`, `zbox park bots`): `resolveSandbox` in `cmd/resolve.go` tries an argument shaped like an id (`^[a-z0-9]{8}$`) as one first and keeps it when it exists, otherwise looks the name up among the sandboxes that are not TERMINATED or ARCHIVED (a name is unique among live ones, the orchestrator refuses a duplicate at create, dead rows may reuse it); no match keeps the API's `sandboxNotFound`, several would name the ids. It runs as the `PreRunE` of the commands (`sandboxArgs`, `sandboxArgsAll` for `rm`) and rewrites the arguments in place, so the command bodies keep taking ids. Session, snapshot, lineage, export, webhook, credential and quarantine ids are not sandboxes and stay ids.
- `GET /sandbox-list` takes `status` as a repeatable string list since 2026-10-01 (`status=RUNNING&status=FAILED`, no longer a single enum; without it the live sandboxes, TERMINATED and ARCHIVED excluded; an unknown value is a 400 `invalidUserInput` with the valid set under the `status` metadata key). `zbox ls --status` is repeatable and also splits commas (`statusList`), upper-cases, and sends nothing when empty. Since 2026-10-09 evening it also pages like `/operation-list` (`limit` up to 1000, `beforeId` the last id of the previous page, rows newest first by created with the id breaking ties, an unknown `beforeId` is a 404 `sandboxNotFound`), but without `limit` it still answers every matching row, so `zbox ls` stays unpaged by default and `--json` complete; `--limit n` asks for the newest n (`listSandboxes` in `cmd/sandbox.go` walks pages when n is over 1000, like `listOperations`) and `--before <id>` continues from a cursor. There is no `--all`, the default is already everything.
- `exec` and `process` take argv after `--`, no shell. `zbox exec` exits with the remote exit code.
- `zbox shell` speaks the PTY WebSocket: the first server frame is text `{"session":{id,ticket}}`, binary frames are terminal bytes, a text `{"resize":...}` follows SIGWINCH. Shell exit closes 1000, a refused open or resume closes 4000 with `<code>: <message>` as the reason (`closeReason` turns it into the usual `ApiError`), only a 1006 is a real drop: it is resumed with `?sessionId=&sessionTicket=` for a minute, and a resume answered `sessionNotFound` means the shell had exited meanwhile, so the command ends cleanly. Stdin is read once and handed to the current connection so a reconnect loses nothing.
- `zbox webhook create` with no `--event` (or `--event all`) sends an empty list, which the contract reads as every event; listings print it as `all`. The signing secret is printed once at creation. `zbox ssh-key` takes a public key file, not the key text, and serves an image's own sshd only. `zbox ssh <id|name> [-- ssh args]` (`cmd/ssh.go`, 2026-10-14) execs the local `ssh` with a ProxyCommand of the hidden `zbox ssh-proxy <zbox-id|id>`, which relays stdin and stdout over `GET /sandbox/{id}/ssh/connect` (binary frames carry the SSH wire protocol to the agent's own server, no client auth, the API authenticated the caller) and pins the host key from `GET /sandbox/{id}/ssh` (`hostKey`, null on a sandbox from before the server, which the next wake fixes) into `~/.config/zbox/known_hosts` under the alias `zbox-<id>`; `zbox ssh-config [--install]` prints or writes the `Host zbox-*` block (`~/.config/zbox/ssh_config`, included first in `~/.ssh/config`) so plain ssh, scp, sftp, sshfs, rsync and the editors reach `zbox-<id>`. The proxy pins too, so a host ssh never saw verifies. A `--workspace` of the `zbox ssh` run is carried into the ProxyCommand. `zbox park --no-memory` (2026-10-14) sends `memory: false`, the shutdown whose wake is a cold boot; `zbox get` says `delivered, no fork` for a secret-bearing sandbox (parks keep memory for every sandbox, the design's memoryless park is not applied), and a first secret selection makes a sandbox stale like a changed one, so an implicit wake is refused until `wake --redeliver-secrets`. The credential proxy behind the `http://<label>.int.<ingress-host>/` address exists on the Firecracker substrate (the label lands in the guest's `/etc/hosts` at boot and on a live attach or detach; the proxy strips the Authorization and X-Api-Key the sandbox sent and injects the integration's credential as bearer, basic or a named header; peer attachments answer 501). Connectors (`zbox connector`) are the fixed catalogue on top of it: `claude`, `github`, `codex`, each a Workspace env (`CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY`, `GH_TOKEN`, `OPENAI_API_KEY`) plus the integrations it manages (`claude`, `github` and `github-api`, `openai`). `zbox connector set <name>` reads the value without echo or whole from a pipe, never from argv, and `PUT /connector/{name}/credential` stores it as a secret service env and applies it live; `unset` blanks the env and keeps the integrations; `login <name>` posts `/connector/{name}/login` and attaches the terminal (`attachShell`, the shell's resume path with the returned `sessionId` and `sessionTicket`, the session is detached with the 60 s grace running, so attach at once) to the helper sandbox where the provider's login command runs; the orchestrator harvests the credential from the terminal output, stores it and terminates the helper, which closes the shell with 1000, and the command then reads the connector back and fails unless it is CONNECTED. A connected connector makes `zbox new --integration claude --integration github --integration github-api` hand the sandbox the proxied endpoints with a placeholder token (`ANTHROPIC_BASE_URL`, a git `url.insteadOf` rewrite through `GIT_CONFIG_*`, `GITHUB_API_URL`), which is set only at create, fork, restore and a redeliver wake; `--secret <env>` delivers the real credential instead and wins over the placeholder. A ChatGPT login is stored as `CODEX_AUTH_JSON` and only delivered, as `/root/.codex/auth.json`.
- `GET /operation-list` is paged since 2026-09-21: newest first, 100 rows by default, 1000 at most, `beforeId` continues with older ones. `zbox operation ls` prints that default page, `--limit` asks for a number and `--all` pages back through everything (`listOperations`); `childOf` relies on a fresh spawn's operations being within the newest page of its sandbox. `zbox events` with no cursor asks for `newestFirst` and prints the answer turned around, so the latest event is the bottom line (`--before <id>` pages back, `--json` keeps the API's order); `--after` is the old oldest-first long poll and `--follow` the stream. The stream with no `afterId` replays the whole log, so `--follow` without `--after` first reads the newest event id and follows from there. `--sandbox`, `--parent` and `--peer` take a name like the arguments (`resolveFlag`).
- `zbox mcp` (`cmd/mcp.go`, official `modelcontextprotocol/go-sdk`) serves the workspace as a stdio MCP server for Claude Code (`claude mcp add zbox -- zbox mcp`): `run_code {code, language, sandbox_id?, keep?, timeout_seconds?}` spawns from `--template` (the first READY one by default, `--base` for a cold boot), runs `python3 -c` / `node -e` / `bash -c` in `/workspace` and terminates the sandbox unless `keep`, answering stdout, stderr, the exit code and `create_ms` / `run_ms`; `kill_sandbox` terminates a kept one. The exec timeout is capped at 50 s because the edge answers 504 for any API request over 60 s. A sandbox passed by id is never destroyed by `run_code`. The text content is the readable transcript form, the structured content the same fields.
- `GET /workspace` carries `capacity` (`{cpus, memoryBytes, diskBytes}` of the VM as detected on the host: cores, MemTotal, the size of the data volume) and `usage` (`{runningSandboxes, parkedSandboxes, cpus, memoryBytes, diskBytes}`: cpus and memory are the sizes reserved by the RUNNING sandboxes, disk is the used space of the data volume across bases, templates, sandboxes and snapshots) since 2026-09-22. `zbox workspace status` prints them as `Capacity:` and `In use:` lines under the orchestrator line (skipped when an older orchestrator answers zeros), `zbox workspace get` as fields (`capacityString`, `usageString`). Since 2026-10-08 it also carries `imageRelease`, the alias the Workspace VM's image was built under (null on an image from before the record), the `Image` field of `zbox workspace`, and since 2026-10-09 `host` (kernel, CPU and nested virtualization facts, Firecracker and guest kernel releases, agent digest, image build time and apt snapshot, data volume, restore backing and THP, slots, process start), the `Host:` block of `zbox workspace` (`printHost`).
- Policies (workspace, template, sandbox) are edited as JSON files: print, edit, `-f file` back. `zbox policy <id>` prints the shape `-f` takes, generation included.

## Iteration loop

Build straight into the user's PATH after every change, they test by hand from there:

```sh
go build -o ~/.local/bin/zbox ./cmd/zbox
```

`zbox login` and `zbox register` use the public API's device login since 2026-10-13 (`internal/zerops/auth.go`): `POST /auth/device-login` with `appCode: zbox` (a PUBLIC row of the `loginApp` table, added by a nest migration the same day next to `zcli`) answers a request id, a poll secret, a user code and the consent page URL `https://<gui>/authorize-login?request=<id>`; the CLI prints the code, opens the URL (`browser.Open`, nothing listens on this machine), and polls `POST /auth/device-login/check` every `interval` seconds until the user approves (the consent page signs in or registers first, `zbox register` opens the same URL), denies, or the request expires after 5 min. An approval answers a session, which the CLI stores as `config.Session` (`accessToken`, `expiresAt`, `refreshToken`) and refreshes itself: `zeropsClient` in `cmd/root.go` calls `POST /auth/refresh` when under a minute of the access token is left, saves the new pair and, since a refresh kills the old pair and two zbox runs can race, reads the file again before and after a refusal; a dead refresh token (24 h unused) ends in "the Zerops login ran out". **The CLI mints no personal access token any more** (the user's rule of 2026-10-13). `--token` stores a personal access token made in the Zerops GUI as `config.Token`, used as is; `--email` (with `--password`, asked for without echo) opens the session through `POST /auth/login` (registration through `POST /user/registration`) and cannot answer two-factor authentication. `zbox logout` posts `/auth/logout` for a session. Secrets of the account need sudo mode (`ZBOX_WORKSPACE_API_KEY` for `zbox workspace key` is REDACTED outside it whatever the role): `ensureSudo` in `cmd/auth.go` asks `GET /auth/sudo` and runs `POST /auth/device-login/sudo` through the same consent page, which the approving browser session has to pass in sudo mode itself; a personal access token cannot enter sudo this way. The consent page origin is the API's; `guiUrl` in the config or `--gui-url` replaces it for the GUI dev server (`npm start zerops` in `~/code/zerops/frontend`, `http://localhost:1111`, targeting futon since 2026-10-13; `zbox login --gui-url http://localhost:1111` stores it for the logins and sudo consents that follow, `--gui-url=` with an empty value brings the API's page back), and has to target the same API or the session is for another environment. The loopback hand-over through the GUI's `/authorize-app` (the Zerops Code machinery) was the login until that day; the GUI keeps the page for Zerops Code, its zbox mode is gone.

## Reaching the workspace

Since 2026-10-13 a workspace of the account is reached through **zproxy**, not at its subdomain, and the CLI holds no workspace key for it. The flow, all of it existing nest machinery mapped that day: `POST /api/rest/public/service-stack/{id}/ui-access` on the public API (the Zerops token, BasicUser or above on the stack, no body; `zerops.Client.UiAccess` posts it by hand, the released `zerops-go` SDK has no such call yet) answers `{accessToken, expiration, urlUi, urlApi}`; zbusiness reads the stack's `ZBOX_WORKSPACE_API_KEY`, decrypts it and hands it with the container id and port 8080 to zipmaster, which writes one redis record under the token (`WithUiAccess(8080, database, KeyApiKey)` on the `sandbox_workspace` controller in `pkg/zerops/zhared/serviceStack/serviceStack_sandbox_workspace.go`). zproxy (`pkg/zerops/zinfrastructure/zproxy/service/uiProxy`) serves it two ways: the browser form `https://proxy.<domain>/service-ui/<token>/...` (`urlUi`, the token in the path, what the Zerops GUI's "open UI" and `zbox workspace console` use) and, since the nest change of 2026-10-13, the header form `https://proxy.<domain>/service-api/<path>` (`urlApi`) with `Authorization: Bearer <accessToken>`, which is the one the CLI uses, since the user's rule is that no token ever sits in a URL. zproxy checks the token, strips the prefix, tunnels through the instance's zl3balancer into the VM's 8080 and swaps the bearer for the workspace key, so the orchestrator sees an ordinary keyed request and the client (`api.New(urlApi, token)`) is the same as in direct mode. The token lives an hour past its last use (sliding, re-armed on every request, revalidated against redis at most once a minute); a dead one answers 401 with `X-Zerops-Ui-Session: expired` and JSON, on which the client's `Renew` mints a new one and repeats the request (`connect` in `cmd/root.go` wires `mintAccess`, which saves every fresh access with `config.SaveAccess`); a 401 without the header is a client bug or the orchestrator refusing the key and is not renewed. `POST /service-api/logout` with the bearer burns the token (204, idempotent; `api.Workspace.Logout`). WebSockets and streaming pass, nginx's shared `/service-ui/` and `/service-api/` location has request buffering off, 1 h timeouts and `client_max_body_size 0` (the build context upload needed that). Verified on futon 2026-10-13 against `zboxapi` once nest deployed the prefix: status, listings, the event-stream WebSocket, a build-context upload (`base build examples/hello-base`, 12 s), `new`, `exec` and `rm` all through `proxy.app-futon.zerops.dev`, and a token overwritten with garbage in the config was renewed transparently by the next `zbox ls`. The token is pinned to the container at mint time, which is fine since the workspace VM is never recreated; a stopped service answers `serviceStackNoActiveContainer` (the CLI says the workspace is not running, exit 7), a read-only role `insufficientPermissions`.

Modes in `config.Workspace`: an entry with a `serviceId` is a workspace of the account (`Direct()` false) and carries the cached `access {url, token}`; an entry without one is **direct**, the escape hatch kept for scripts without a Zerops login and for another account's workspace, stored by `zbox workspace use <url> --api-key <key>` and reached at its API host with the key, the `ZBOX_WORKSPACE_URL` and `ZBOX_API_KEY` pair being the one-run form of the same thing. Entries are told apart by the service id, or the URL for a direct one (`Same`, `identity`), so a workspace of the account may have no `workspaceUrl` at all (`--no-subdomain`); `Label()` is the host or the service id for messages. `zbox workspace authorize <service-id>` stores a workspace of the account without any browser: it reads the stack for the name and project, mints the first access as the proof the account reaches it, and keeps the API host out of the service env `zeropsSubdomain` (one URL per published port, API first, `zerops.SubdomainHosts`). `zbox setup` stores the service as soon as the import answers (so a failed setup can be torn down), waits for the processes, mints the access (`waitForAccess` waits out the moment before the container is ACTIVE), pings through zproxy, keeps the API host the same way and publishes the ingress host as the workspace's first domain (`PUT /workspace/domains`, dash form); it reads no key. `zbox workspace key` reads `ZBOX_WORKSPACE_API_KEY` from the service through the public API for the user (a personal token gets it in clear, a read-only role `REDACTED`, refused by `keyReadable`), for `use --api-key` on a machine without the login. `zbox workspace console` on a workspace of the account mints a fresh access of its own for the browser and opens `urlUi`, never the CLI's token; on a direct one it keeps the console login-ticket flow. The console (`service/console/handler.go` in the orchestrator) already renders under `X-Zerops-Ui-Base`. Sandbox port URLs and `zbox open` need a workspace domain (since 2026-10-14 the orchestrator's own list, `GET /workspace` `domains[]`, `zbox workspace domain ls|add|rm`; the platform sets nothing but the two secrets): the dash form `{port}-{id}-<domain>` is the ingress subdomain host, which `zbox setup` adds when subdomain access is on, the dot form `{port}-{id}.<domain>` an own wildcard domain `*.<domain>` the user routes to port 8081 in the Zerops GUI (DNS A, AAAA and the ACME CNAME the GUI shows); a sandbox lists one URL per domain in list order and `zbox open` takes the first. So `enableSubdomainAccess: true` stays in the import by default and `zbox setup --no-subdomain` (opt-out, the user's choice of 2026-10-13) leaves it out: such a workspace has no domain unless one is added, empty `hosts`, no `zbox open`. The connector proxy name inside a sandbox is the fixed `int.workspace`. The setup summary says so.

`zbox workspace ls` lists the workspaces of the logged-in account, which are its Sandbox Workspace services (one service stack search on `clientId` and `serviceStackTypeId` `sandbox_workspace`, `zbox@1` is only the import alias of that type; the docker services the v0 workspaces were imported as are not listed since 2026-09-21, when the docker substrate was removed from the orchestrator, and one this machine still holds a key for shows up among the ones not in the account; the search index does not carry `recipeSource`, so the marker is only sent on import), with the name and an asterisk for the ones this machine holds a key for, and the `use`-assigned ones that are not in the account after them; not logged in, it lists the known ones. Config keys: `projectId`, `serviceId`, `workspaceUrl` (the API host when the service has subdomain access), `access` (the zproxy access, see above) and, for a direct workspace, `apiKey` are the workspace in use, and `workspaces` is the list of known ones (the same fields plus the name), the current one included. Every reader keeps using the flat fields; `zbox workspace switch <name|host|prefix|service id|project>` copies another entry into them without contacting anything (`config.Lookup`, see the override below for what it matches), `zbox workspace ls` lists the account's workspaces with the known ones marked, `zbox setup --name`, `zbox workspace use --name` and `zbox workspace authorize --name` add entries (a name in use by another workspace is refused, the default name of a `use` is the first host label), teardown (which deletes only the workspace service, never the project, so it also works on an authorized workspace) and forget drop the current one and name the others. A config from before the list gets its flat workspace as the one entry at load; a config from before zproxy keeps the `apiKey` of its account workspaces in the entries, unused. `ZBOX_WORKSPACE_URL` and `ZBOX_API_KEY` override the workspace for one run with a direct pair (only as a whole since 2026-10-14, half a pair is a usage error from `loadConfig`, `config.HalfEnvPair`, and the pair never takes the current workspace's stored key), `zbox workspace use <url> --api-key` assigns a workspace the CLI did not create (no Zerops ids, so no teardown).

The global flag `--workspace <ref>` and the env `ZBOX_WORKSPACE` (since 2026-09-29, the flag wins) name a known workspace for one run and leave the current one as it is, which is how two sessions share one `config.json`: the nest session runs its benchmarks against `zboxbench` while the user keeps using their own. The ref goes through `config.Lookup`, against the stored `workspaces` only, nothing is contacted: a whole match on the name, the service id, the project name or id, the API URL or host, and only when nothing matches whole a prefix of the name or the host. A ref that fits several workspaces is refused with the candidates (name, project, service id, host), never settled by the order of the list, so a project that holds two workspaces does not name either; the service hostname is not stored and matches only as the default name of an authorized workspace. An unknown ref or an entry that is neither of the account nor a URL and key pair (`Usable`) fails with the hint to `authorize` or `use`. The mechanism is `config.Pin`: it answers a copy of the config whose flat fields show the named workspace and keeps the stored selection in the unexported `pinned`, which `Save` writes back, so every reader of the flat fields works unchanged and an override never becomes the current workspace; `EffectiveWorkspace` does not let `ZBOX_WORKSPACE_URL` and `ZBOX_API_KEY` override a pinned workspace, and `ZBOX_WORKSPACE` beside either of them in the environment is refused as contradictory. In `cmd`, `loadSelected` is the pinned config and what the commands that work on a workspace read (`workspace()`, `ensureWorkspace`, `status`, `teardown`, `workspace forget`), `loadConfig` stays the stored one for the commands that manage the selection (`switch`, `use`, `authorize`, `setup`, `workspace ls`, the login ones). So `teardown` and `forget` under an override act on the named workspace and the current one stays (`ForgetWorkspace` falls back to the stored selection, unless that was the very workspace). `zbox workspace switch <ref>` and `zbox setup` refuse to run under an override (`refuseOverride`), `zbox workspace switch` with no argument still lists. `zbox workspace use` under an override only stores the workspace (`Remember` instead of `Assign`) and the ref has to resolve to the workspace being stored, so a `ZBOX_WORKSPACE` left in the environment cannot pass for a request to keep the selection; `authorize` is unchanged, it only ever stored. The listings mark the named workspace with `>` beside the `*` of the current one and explain it in a line underneath (`mark`, `printMarks`), an unresolvable ref does not fail a listing, and `zbox workspace status` names the override on its Workspace line.

Hidden flags: `--public-api-url` (default futon since 2026-10-01, alpha from 2026-09-22 before that, `config.DefaultApiUrl`; a stored `apiUrl` wins, and `zbox login --public-api-url <url>` is how a config moves environments: since 2026-10-14 the flags hold for one run through `config.Override` and `Save` writes the stored URLs back, so a refresh or an access mint on the way cannot persist them, and only the login adopts them, `AdoptOverrides` in `finishLogin`), `--gui-url`. ## Setup and the default base

Since 2026-10-06 the Sandbox Workspace type `zbox@1` (alias `zbox@latest`) is a managed (STANDARD) service type, no longer a runtime: no appVersion, no deploy, no zerops.yml, and the import refuses `minContainers`, `maxContainers`, `zeropsSetup`, `zeropsYaml` and `buildFromGit` for it. The import YAML (`internal/zerops/import.go`) is the type, `enableSubdomainAccess: true`, `verticalAutoscaling` with min equal to max for each resource given (none by default since 2026-10-09) and, until 2026-10-09, the env `ZBOX_WORKSPACE_BASES`, which the CLI no longer sets. The controller publishes the two http ports itself (8080 API, 8081 ingress) and writes `zeropsSubdomain` as two lines, the API host first, which zsc copies into the orchestrator's config file; the router listener defaults to 8081 in the orchestrator config. Readiness is the API on 8080, setup never waits on 8081. The service is an Ubuntu VM in which the orchestrator runs Firecracker guests (its only substrate since 2026-09-21: the docker one and the `ZBOX_SUBSTRATE_KIND` env are gone, and the `substrate` field of `GET /workspace` only ever says FIRECRACKER), pinned to one container sized by the platform's defaults for the type unless `--cpu`, `--ram` or `--disk` pin a resource (since 2026-10-09; 24 dedicated cpus, 128 GiB and 250 GiB were the CLI's defaults from 2026-09-22, sized for the alpha metal nodes; the type has no vertical scaling, which the API enforces by refusing a differing pair, and the driver floor is 2 cpu, 2 GiB, 10 GiB, which `RenderImport` refuses to go under). The disk is the XFS data volume at `/var/lib/zbox`, one shared pool for every base, sandbox disk, park image and snapshot (a sandbox root is a sparse 10 GiB image from the orchestrator config, not a per-sandbox share of it), the root disk is a fixed 5 GiB, and guests take their RAM from the VM's, 512 MiB each by default (since 2026-10-14, 1 GiB before). Since 2026-10-07 zsc runs the mounted `/opt/zerops/bin/zerops-zbox-orchestrator` from the image like this, everything as root (no sudo re-exec any more): before every start it writes `/etc/zerops-zbox-orchestrator/config.yml` (root, 0600) from the service env, `zbox.workspace.{apiKey, volumeKey, apiHost, ingressHost, bases}`, the hosts taken from the two `zeropsSubdomain` URLs (API first), the bases from the plain user env `ZBOX_WORKSPACE_BASES`, and the orchestrator reads only that file for its own configuration, no service env; then it writes and starts the systemd unit `zerops-zbox-orchestrator` (`ExecStartPre=/opt/zerops/bin/zerops-zbox-orchestrator prepare`, `ExecStart=... run`, root, no zenv) and waits for `GET /api/rest/ping`. The unit's prepare opens the data volume (since 2026-10-07 LUKS2 around XFS, the passphrase is the generated non-editable system env `ZBOX_WORKSPACE_VOLUME_KEY`; a blank disk is formatted, a grown disk grows the mapping and the filesystem), checks the image contract, loads kernel modules and sysctls, fetches the guest kernel, builds the nft table and applies the SQLite schema migrations. zsc never runs prepare itself: the unit prepares on its own, so a VM power cycle the platform does without zsc hooks (a disk change) comes up too. Nothing from the import runs commands. The orchestrator logs to the local syslog under the tag `zerops-zbox-orchestrator`, zsc's own lines are tagged `zerops@setup`, and both reach the project log (`zcli service log`, the GUI), the prepare lines included. The orchestrator carries no key of its own since 2026-09-17: the controller generates the sensitive system env `ZBOX_WORKSPACE_API_KEY` at service create (like the Qdrant `apiKey`), and since 2026-10-07 it reaches the orchestrator only through the config file. The bases came from `ZBOX_WORKSPACE_BASES` until 2026-10-09 (the platform side still honours it, the CLI registers every base through the API now, see the setup chain above): image references or `docker save` tarball URLs separated by whitespace or commas, each pulled and flattened by `run` in the background once the API listens (since 2026-10-07 evening; `prepare` pulled them before the unit for a few hours that day, which made a slow registry gate the service start), so the service turns ACTIVE before the bases are in place and the setup wait covers the pull (a few minutes on a first setup; idempotent per digest; a failed pull is a line in the project log, the base has no row, `zbox base ls` shows nothing for it, the next start tries again). The platform has no default, `zbox setup` writes the image (`--image`, the tarball URL by default) as the value and the GUI will too. An edited `ZBOX_WORKSPACE_API_KEY` or `ZBOX_WORKSPACE_BASES` takes effect on the next explicit restart, stop and start, or reload of the service, never on its own; the reload (on the type since 2026-10-07) is the cheap way, it runs stop unit, config, unit, start (the unit prepares) without rebooting the VM, so the sandboxes stay up, while a restart reboots the VM and parks every sandbox. So adding a base to an existing workspace is an edit of the env and a reload, which replaces the old `zcli push` of a rendered yaml. `RenderImport` holds the image to a plain reference charset, since the value is split on whitespace and commas. Templates are not built at start any more: `zbox setup` creates them through `POST /template` once the base is READY (point 3 of the nest brief of 2026-10-06), one after the other, each a step on the waiting screen ("Building the warm template dev"), with name, the base digest, memory, cpus, warm true and the warm-up, exactly what `zbox template create --warm` sends (`createSetupTemplate`, `waitTemplate` in `cmd/base.go`); `--template name=cpus:memory@base` names each one (`dev=2:4g@hello`), none are built by default since 2026-10-09 (the defaults `dev:4g:2` and `big:16g:4` before that, and the `--template none` that opted out of them is gone), `--warmup name=command` is repeatable with one per template name (`setupTemplates`, `setupTemplate` in `cmd/setup.go`). The VM names on the node are `<hostname>-db-1-N` since the type change (the driver service key is `db`), `<hostname>-runtime-1-N` before. `prepare` mounts the data disk at `/var/lib/zbox`, and there is no image load, no docker. A workspace cannot be re-deployed any more, there is nothing to deploy; a service stop and start keeps the data. The runtime-era yaml with the init commands (`migrate`, `host prepare`, `base ensure`, `template ensure` lines) is in git history (v0.16), the docker@26.1 template before it (v0.5); the init-command era of 2026-10-06, in which zsc ran `host prepare`, `migrate` and `base ensure` lines and `run` through zerops-zenv, lasted one day.

`zbox setup` imports the service with `recipeSource: zeropsio/zbox` in the request body (the marker the Zerops GUI lists workspaces by, `zeropsSetup` is not returned by the public API), waits for the Zerops processes, reads `zeropsSubdomain` and `ZBOX_WORKSPACE_API_KEY` from the service envs (the key through the GUI hand-over when the env list does not give it to a token), waits for `GET /workspace` to answer with the key, then waits for the default base (the tarball URL, `--image` overrides): the row appears only when the pull is done, which `run` does in the background right after it listens, so `ensureBase` finds the row at `GET /base-list` by image ref within a minute or two (stored verbatim, and a digest registered again under another reference takes the newest one) and waits for READY (`setupBaseTimeout`, 15 min); it keeps looking for `setupBasePoll` (3 min), and only when no row shows up in that time, which is what a failed pull looks like, does it register the image through `POST /base` itself and get the pull's error back (a second pull of a registered ref is a no-op on the digest, so the fallback is safe, just slower). The answer is READY or `substrateFailed`. A workspace with no ready base cannot serve `zbox new`. A guest on this type reaches the internet and the project DNS, but not the workspace itself or other sandboxes. The docker-era workspaces on futon (such as `zbox` of project zbox-test) cannot run the orchestrator any more, it has no docker substrate; do not deploy to futon from here. A fresh `zbox setup` never sees the generated key, zproxy does. Per-port ingress URLs work on futon since the edge change of 2026-09-14 (the project L7 config gets a regex alias per subdomain host); every URL in `hosts` is reachable, all access modes, wake-on-request and GONE verified. A port nobody listens on behind the edge answers the platform's HTML 502 page after about five seconds, not a router JSON error, and parking kills every session in the sandbox, so a server started with `zbox process` is gone after a wake.

The import YAML lives only in `internal/zerops/import.go` now: the retired `../zbox-gui` held a copy and the Zerops GUI does not create workspaces. The template is owned by the nest side (it mirrors what the controller of the type accepts), so a template brief from the nest session is applied as given, and a change made here is reported back there.

## The setup wait

`zbox setup` takes minutes and has almost nothing to print, so `internal/waiting` fills it with plain text: each stage is a line with trailing dots and, on a TTY, a dimmed note about workspaces follows every nine seconds. It used to be a redrawn frame with a wavy `zbox` wordmark and a progress bar, the user asked for text only (2026-09-16), so nothing is redrawn and there is no `--estimate` any more. Rules that package lives by:

- Stdout that is not a TTY (a pipe, CI) gets the stage lines only, and `NO_COLOR` drops the dimming.
- `Pause`/`Resume` hold the notes while the caller prints and reads on the terminal (the browser hand-over), so a note cannot land in the middle of a prompt.
- The Zerops processes behind the import are deliberately not shown, the step name is the whole status. A failed process still fails the setup with its own message.
- The notes were duplicated in the retired `../zbox-gui` (`src/lib/notes.ts`); a GUI that draws the same wait should reuse them. They are only ever accurate, useful things about a workspace: no jokes, no filler, and never soften a cost or a restart. Keep them to a sentence or two, they wrap like any other line.

## Gotcha

The public API answers a deleted project or service with **HTTP 400 and code `projectNotFound` / `serviceStackNotFound`**, not 404, even though the ACL middleware that raises them was meant to answer 404. `zerops.IsNotFound` matches the code and accepts 404 too, so a fix on the API side keeps working. Use it instead of checking the status.
