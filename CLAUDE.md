# zbox CLI

Wrapper around the zbox orchestrator. The standalone `../zbox-gui` is retired: the per-workspace console is served by the orchestrator, the Zerops GUI (`~/code/zerops/frontend`) does login, register and the workspace key hand-over, and the CLI lists, creates and deletes workspaces itself. The orchestrator itself lives in `../nest` (`pkg/zerops/orchestrator/zbox`, branch `z0-zbox`), design in `../nest/sandbox-workspace-architecture.md`, decisions and gotchas in `../nest/pkg/zerops/orchestrator/zbox/CLAUDE.md`, older notes in `~/.claude/plans/zbox.md`.

Terminology: one Zerops service is one **workspace**. Say "workspace" in code and output, never "pool". The persisted key `serviceId` in `config.json` keeps its spelling.

## The contract

The API is `../nest/pkg/zerops/orchestrator/zbox/generated/openapi/restPublic/openapi.yml` (78 routes, v0, bearer API key on everything but ping). The CLI is built against the contract, not against the deployed backend: the nest session implementing the endpoints announces finished route groups, and every route exists as a stub until then. Nothing exists in the CLI that is not in the spec.

Contract changes go through the nest side. If a shape blocks the CLI or is wrong for it, name the route and the reason to the nest session, do not work around it locally.

## Generated client

`internal/api/gen.go` is generated by oapi-codegen (a `tool` directive in `go.mod`, config `internal/api/oapi.yaml`) straight from the nest file. Regenerate after every spec change:

```sh
go generate ./internal/api
```

`internal/api/client.go` is the hand-written wrapper: `Workspace` (the generated type is already called `Client`) adds the bearer, mints an `Idempotency-Key` per capacity-consuming call (`Key()`), decodes every 200 into the shared `Base*` type and every error into `ApiError`, and adds the waits (`WaitOperation`, `WaitSandbox`) and the two WebSocket routes (`Shell`, `StreamEvents`). The contract types timestamps as plain strings (`format: dateTime`), `api.Time` parses them. Both error shapes are decoded, the flat `{code, message}` of the spec and the `{"error": {...}}` envelope of the shared HTTP server.

## Command conventions

- Every command takes `--json` and then prints the API objects untouched. The text form goes through `emit(v, func())` in `cmd/root.go`.
- Mutations that answer with an operation wait for it by default and exit non-zero when it fails, `--no-wait` prints the operation instead. An `operationInFlight` answer (another capacity operation still runs, its id in the error metadata) makes the command wait on that operation and retry once, unless `--no-wait`. `invalidSandboxStatus` is a settled state that does not allow the verb and is reported as is. `zbox new`, `fork` and `restore` answer with a Spawn (operation plus rows), `runSpawn` waits on the operation and re-reads the rows.
- Bases and templates are addressed by digest, digest prefix, image ref or name (`findBase`, `findTemplate`). `zbox new` with no `--base` uses the only ready base and refuses to guess between several. `zbox template create --warm` boots the base once and snapshots its memory: the row is BUILDING until READY (`hasMemory` true, about 18 s on futon) or FAILED with `failedReason`, and the command waits unless `--no-wait`. `--memory` and `--cpus` set the size the image is taken at, which is also the default of every sandbox spawned with `--template`; a spawn that names another size cold boots from the base instead of resuming (about 8 s against 2 s). Deleting a building template answers `inUse`. The receipt of a finished boot operation (CREATE, WAKE, FORK, RESTORE) is the free `result` object, `{address, resumedMemory, secretsDelivered}` (PARK gives `{memoryKept}`); `bootNote` reads `resumedMemory` and `zbox new`/`fork`/`restore` print `Boot: resumed from memory` or `cold boot` under each row (`childOf` finds the row's child of the bulk operation), `wake` appends it to its line, `zbox operation get` prints the whole result.
- Ports are declared in the sandbox policy: `port[/protocol][/access]` (`3000`, `3000/public`, `5432/tcp/project`, plus `websocket`, `wake` and `no-wake` tokens; public ports do not wake a parked sandbox unless `wake` says so). `zbox port open|close` read the policy and write it back under the generation they read, so a concurrent edit is rejected rather than merged. The URL of a port is `{port}-{id}-{ingress-host}`, the API returns it in `hosts`, which is derived from the HTTP ports only, so port listings read `policy.ingress.ports` and attach the URL where one exists. Text output prints URLs ready to open (`openUrl`): a MEMBERS port carries `?apiKey=<workspace key>`, `zbox cred issue` prints the port URL with `?ticket=` or `?token=` and the fresh secret, the router exchanges the parameter once for a `zbox_session` cookie and redirects to the clean URL. PUBLIC stays bare, PROJECT has no URL. `--json` prints the API objects untouched, so the bare `hosts` are there.
- `zbox new` on a plain image such as `alpine` needs a long-running command after `--` (docker runs the image contract as the container command), otherwise the sandbox fails at once.
- `exec` and `process` take argv after `--`, no shell. `zbox exec` exits with the remote exit code.
- `zbox shell` speaks the PTY WebSocket: the first server frame is text `{"session":{id,ticket}}`, binary frames are terminal bytes, a text `{"resize":...}` follows SIGWINCH. Shell exit closes 1000, a refused open or resume closes 4000 with `<code>: <message>` as the reason (`closeReason` turns it into the usual `ApiError`), only a 1006 is a real drop: it is resumed with `?sessionId=&sessionTicket=` for a minute, and a resume answered `sessionNotFound` means the shell had exited meanwhile, so the command ends cleanly. Stdin is read once and handed to the current connection so a reconnect loses nothing.
- `zbox webhook create` with no `--event` (or `--event all`) sends an empty list, which the contract reads as every event; listings print it as `all`. The signing secret is printed once at creation. `zbox ssh-key` takes a public key file, not the key text. The credential proxy behind the `http://<label>.int.<ingress-host>/` address exists on the Firecracker substrate (the label lands in the guest's `/etc/hosts` at boot and on a live attach or detach; the proxy strips the Authorization and X-Api-Key the sandbox sent and injects the integration's credential as bearer, basic or a named header; peer attachments answer 501). Connectors (`zbox connector`) are the fixed catalogue on top of it: `claude`, `github`, `codex`, each a Workspace env (`CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY`, `GH_TOKEN`, `OPENAI_API_KEY`) plus the integrations it manages (`claude`, `github` and `github-api`, `openai`). `zbox connector set <name>` reads the value without echo or whole from a pipe, never from argv, and `PUT /connector/{name}/credential` stores it as a secret service env and applies it live; `unset` blanks the env and keeps the integrations; `login <name>` posts `/connector/{name}/login` and attaches the terminal (`attachShell`, the shell's resume path with the returned `sessionId` and `sessionTicket`, the session is detached with the 60 s grace running, so attach at once) to the helper sandbox where the provider's login command runs; the orchestrator harvests the credential from the terminal output, stores it and terminates the helper, which closes the shell with 1000, and the command then reads the connector back and fails unless it is CONNECTED. A connected connector makes `zbox new --integration claude --integration github --integration github-api` hand the sandbox the proxied endpoints with a placeholder token (`ANTHROPIC_BASE_URL`, a git `url.insteadOf` rewrite through `GIT_CONFIG_*`, `GITHUB_API_URL`), which is set only at create, fork, restore and a redeliver wake; `--secret <env>` delivers the real credential instead and wins over the placeholder. A ChatGPT login is stored as `CODEX_AUTH_JSON` and only delivered, as `/root/.codex/auth.json`.
- Policies (workspace, template, sandbox) are edited as JSON files: print, edit, `-f file` back. `zbox policy <id>` prints the shape `-f` takes, generation included.

## Iteration loop

Build straight into the user's PATH after every change, they test by hand from there:

```sh
go build -o ~/.local/bin/zbox .
```

`zbox login` and `zbox register` open the Zerops GUI by default and receive a personal access token on a loopback hand-over (`internal/browser`), the machinery Zerops Code uses: the CLI opens `<gui>/authorize-app?app=zbox&state=<nonce>&port=<port>` (`&intent=register` for register), the GUI redirects the browser to `http://localhost:<port>/zerops/authorized` with the credential in the **fragment** (`#token=&state=`, or `#error=<code>&state=`), and the callback page the CLI serves posts the fragment to `/zerops/authorized/deliver` and scrubs it from history. The receiver listens on 127.0.0.1 and ::1, checks the nonce, and maps the GUI's codes (`access_denied`, `mint_failed`, `workspace_not_found`, `reveal_failed`, `workspace_not_ready`) to `HandoverError`; `authorize` waits for the `zeropsSubdomain` env before opening the browser so the last one is not met. `browser_test.go` plays the GUI and the browser against it. `--token` stores a given token; `--email` (with `--password`, asked for without echo) logs in from the terminal through `POST /auth/login` and mints the token itself (`POST /user-token`), which cannot answer two-factor authentication and cannot be exercised with a token (`notAllowedForApplicationToken`). The GUI origin is `guiUrl` in the config, `--gui-url` for one run, and by default `http://localhost:1111`, the Zerops GUI dev server on this machine (`~/code/zerops/frontend` against the futon API): a development default until the hand-over is deployed, the deployed origin is not settled.

The same hand-over delivers the workspace API key, which is a generated secret the public API does not reveal to a token: `zbox workspace authorize <service-id>` opens `intent=workspace&serviceStackId=`, the GUI reveals the service env `ZBOX_WORKSPACE_API_KEY` (the user gets a password prompt for sudo mode; since 2026-09-17 there is no fallback to the old `apiKey` env, so a workspace from before the controller answers `reveal_failed` with reason `no_api_key_env` until the env is added by hand), answers `#apiHost=&apiKey=&serviceStackId=&state=`, and the CLI only stores the key: the workspace lands in the list under the service hostname (`--name` overrides) and becomes the current one only when none is (`config.Remember` versus `Assign`). `zbox setup` lands in the same function when the key env is not readable to the token (absent after 30 s, empty, a generator placeholder, or the literal `REDACTED` that a read-only project role gets for a sensitive env; a personal access token is always in sudo mode, so it normally reads the generated key in clear from `GET /service-stack/{id}/env`), with the wait screen paused (`Pause`/`Resume`) while the browser is open, and switches to it. `zbox workspace ls` lists the workspaces of the logged-in account, which are its Sandbox Workspace services (`zbox@1`) plus the docker services the v0 workspaces were imported as before that type existed (one service stack search on `clientId` and `serviceStackTypeId` per type, `sandbox_workspace` then `docker`, since `zbox@1` is only the import alias of that type, the TYPE column tells them apart; the search index does not carry `recipeSource`, so the marker is only sent on import), with the name and an asterisk for the ones this machine holds a key for, and the `use`-assigned ones that are not in the account after them; not logged in, it lists the known ones. The standalone zbox GUI is retired: the per-workspace console is served by the orchestrator at `/` of the API host (`zbox open` opens `/console/login?apiKey=<key>`, which sets the `zbox_console` cookie and redirects to `/`, a wrong key lands on the console's login form; `zbox workspace key` prints the key for pasting), and the Zerops GUI does only login, register and the key hand-over for zbox (`~/code/zerops/frontend`, page `/authorize-app`).

Config keys: `workspaceUrl` (the API host, first line of the service's `zeropsSubdomain`) and `apiKey` (the `ZBOX_WORKSPACE_API_KEY` service env) are the workspace in use, and `workspaces` is the list of known ones (name, Zerops ids, URL, key), the current one included. Every reader keeps using the flat fields; `zbox switch <name|host|prefix|service id>` copies another entry into them without contacting anything, `zbox workspace ls` lists the account's workspaces with the known ones marked, `zbox setup --name`, `zbox workspace use --name` and `zbox workspace authorize --name` add entries (a name in use by another workspace is refused, the default name of a `use` is the first host label), teardown (which deletes only the workspace service, never the project, so it also works on an authorized workspace) and forget drop the current one and name the others. A config from before the list gets its flat workspace as the one entry at load. `ZBOX_WORKSPACE_URL` and `ZBOX_API_KEY` override the workspace for one run, `zbox workspace use <url> --api-key` assigns a workspace the CLI did not create (no Zerops ids, so no teardown).

Hidden flags: `--public-api-url` (default futon), `--gui-url`.

The orchestrator binary is no longer downloaded: since 2026-09-15 it is a zstart user-target package (`zerops-zbox-orchestrator`) mounted into every workspace VM at `/opt/zerops/bin/zerops-zbox-orchestrator`, so an orchestrator change reaches a workspace with the platform and a service restart. `zbox-base.tar.gz` is a `docker save` of the default sandbox image. The docker-era template piped it into `docker load` as an init command; a `zbox@1` workspace has no docker, so the orchestrator pulls it straight from the tarball URL as a `POST /base` image reference (`config.DefaultBaseImage`, what `zbox setup` registers unless `--image` says otherwise; plain registry references such as `ubuntu:26.04` work as well). Verified on futon 2026-09-16: the pull flattens the tarball and answers READY in about 30 s with the same digest the docker path had, and sandboxes boot from it. Re-registering an existing digest is a no-op on this type, the image is kept. Rebuild the tarball whenever the Dockerfile in the orchestrator changes. `--provenance=false --sbom=false` keeps it a plain single-platform image, a loader cannot take a buildx manifest list:

```sh
docker build --platform linux/amd64 --provenance=false --sbom=false -t zbox-base:latest .
docker save zbox-base:latest | gzip -1 > /tmp/zbox-base.tar.gz
mc cp /tmp/zbox-base.tar.gz <alias>/57fhv-s3/zbox-base.tar.gz
```

## Setup and the default base

The import YAML publishes two http ports with subdomain access (8080 API, 8081 ingress, the two lines of `zeropsSubdomain` the orchestrator reads itself, so 8080 must stay declared before 8081), and the router listener defaults to 8081 in the orchestrator config (`ZBOX_ROUTER_ADDRESS`) so no start-command flag is needed. Until the router lands, 8081 answers nothing and setup must not wait on it: readiness is the API on 8080. Since 2026-09-16 the service is the Sandbox Workspace type `zbox@1` (alias `zbox@latest`): an Ubuntu VM in which the orchestrator runs Firecracker guests (`ZBOX_SUBSTRATE_KIND: FIRECRACKER` in the run envs), pinned to one container with two dedicated cpus, 8 GB of RAM and a 50 GB disk (`minContainers`/`maxContainers` 1, `verticalAutoscaling` with min equal to max: the type has no vertical scaling, which the API enforces by refusing a differing pair, and the driver floor is 2 cpu, 2 GB, 10 GB). The disk is the 50 GB XFS data volume at `/var/lib/zbox`, one shared pool for every base, sandbox disk, park image and snapshot (a sandbox root is a sparse 10 GiB image from the orchestrator config, not a per-sandbox share of it), the root disk is a fixed 5 GiB, and guests take their RAM from the 8 GB, 1 GiB each by default. The YAML runs the mounted `/opt/zerops/bin/zerops-zbox-orchestrator` as plain commands: the orchestrator needs root for network namespaces, taps, nftables and the jailer and elevates itself (`run` re-execs under sudo with an explicit env list when the substrate is FIRECRACKER), and the template must not say `sudo -E`, because the image ships sudo-rs, which ignores `-E`, so the orchestrator never saw `apiKey` that way. It carries no key of its own since 2026-09-17: the Sandbox Workspace controller generates the sensitive system env `ZBOX_WORKSPACE_API_KEY` at service create (like the Qdrant `apiKey`) and the orchestrator reads it from its environment (the old `apiKey` env is no longer read, the start line stays a plain command: Zerops runs it through `exec`, so a leading `VAR=value` fails with exit 127), and it runs `migrate` as the only init command (the orchestrator does not migrate at start, `migrate` creates the database when missing, applies the pending migrations and exits non-zero on failure, and `run` on an unmigrated database fails with "no such table"). The image mounts the data disk at `/var/lib/zbox` itself, no mkdir, and there is no image load, no docker. Platform gotcha: data on this type does not survive a deploy or push yet (the VM and its data volume are replaced), only a service stop and start keeps it; a platform fix is coming and setup and teardown are not changed for it. The docker@26.1 template it replaces is in git history (v0.5).

`zbox setup` imports the service with `recipeSource: zeropsio/zbox` in the request body (the marker the Zerops GUI lists workspaces by, `zeropsSetup` is not returned by the public API), waits for the Zerops processes, reads `zeropsSubdomain` and `ZBOX_WORKSPACE_API_KEY` from the service envs (the key through the GUI hand-over when the env list does not give it to a token), waits for `GET /workspace` to answer with the key, then registers the default base (the tarball URL, `--image` overrides) through `POST /base` and waits for it to be READY. The answer is READY or `substrateFailed`. A workspace with no ready base cannot serve `zbox new`. A guest on this type reaches the internet and the project DNS, but not the workspace itself or other sandboxes. On futon the docker-era workspace `zbox` of project zbox-test (API `https://zbox-c-8080.app-futon.zerops.dev`, ingress `-8081`) keeps running the mounted orchestrator on the docker substrate, and the nest session is bringing the first `zbox@1` service up next to it (hostname `zboxfc`); do not deploy to futon from here. A fresh `zbox setup` gets the generated `apiKey` through the GUI hand-over. Per-port ingress URLs work on futon since the edge change of 2026-09-14 (the project L7 config gets a regex alias per subdomain host); every URL in `hosts` is reachable, all access modes, wake-on-request and GONE verified. A port nobody listens on behind the edge answers the platform's HTML 502 page after about five seconds, not a router JSON error, and parking kills every session in the sandbox, so a server started with `zbox process` is gone after a wake.

The import YAML lives only in `internal/zerops/import.go` now: the retired `../zbox-gui` held a copy and the Zerops GUI does not create workspaces. The template is owned by the nest side (it mirrors the run yaml the orchestrator is developed against), so a template brief from the nest session is applied as given, and a change made here is reported back there.

## The setup wait

`zbox setup` takes minutes and has almost nothing to print, so `internal/waiting` fills it with plain text: each stage is a line with trailing dots and, on a TTY, a dimmed note about workspaces follows every nine seconds. It used to be a redrawn frame with a wavy `zbox` wordmark and a progress bar, the user asked for text only (2026-09-16), so nothing is redrawn and there is no `--estimate` any more. Rules that package lives by:

- Stdout that is not a TTY (a pipe, CI) gets the stage lines only, and `NO_COLOR` drops the dimming.
- `Pause`/`Resume` hold the notes while the caller prints and reads on the terminal (the browser hand-over), so a note cannot land in the middle of a prompt.
- The Zerops processes behind the import are deliberately not shown, the step name is the whole status. A failed process still fails the setup with its own message.
- The notes were duplicated in the retired `../zbox-gui` (`src/lib/notes.ts`); a GUI that draws the same wait should reuse them. They are only ever accurate, useful things about a workspace: no jokes, no filler, and never soften a cost or a restart. Keep them to a sentence or two, they wrap like any other line.

## Gotcha

The public API answers a deleted project or service with **HTTP 400 and code `projectNotFound` / `serviceStackNotFound`**, not 404, even though the ACL middleware that raises them was meant to answer 404. `zerops.IsNotFound` matches the code and accepts 404 too, so a fix on the API side keeps working. Use it instead of checking the status.
